## 0. 为什么要单独做一个 skill

| 做法 | 问题 |
|---|---|
| 拆进现有 8 个 forge skill | 同一套规则写 8 遍，每个 skill 变长，迟早各写各的 |
| 只留在 info2action 的 `docs/README.md` | 只对一个项目有效，换项目就丢 |
| 扩展 forge-doc-policy | 它只管「文档放哪」，不管「怎么写、怎么出图、怎么检查」 |
| 扩展 forge-design | 它产出写给 AI 的 DESIGN.md，混在一起会又写回长文档 |
| **单独 skill + 各阶段一行调用** | 规则、模板、脚本只有一份；各阶段只说「收尾时用它更新」 |

四条资格全满足：☑ 每个需求都用 ☑ 「写文档」容易被 forge-prd / forge-design 接走 ☑ 画图、截图、检查都能脚本化 ☑ 写法和维护规则要跨会话一致

## 1. 收料

### 1.1 需求与场景

- **谁用**：产品负责人（读者，注意力有限，要拍板）；AI（作者，每个阶段维护）。
- **现在最烦的**：forge 产出的 PRD、DESIGN、feature-spec 写给 AI 看，太长（DESIGN.md 9,582 行），读不完；迭代中的设计、交互、prompt 调整看不到；文档和代码一路漂移（AI 搜索一次审出约 100 处）。
- **想要的样子**：每个功能一份 `docs/modules/<功能>.md`。开头是待拍板；13 项关键内容按需取舍；先图后字；末尾记关键改动；提到的文件都能点开。
- **什么算做对**
  - 机器可判：检查脚本通过（`watch` 覆盖的文件改了文档也改了；正文没有讲历史的词；关键改动不超过 15 条；图都存在；文件引用都是链接）；正文 10 分钟内读完。
  - 人可判：你读完能回答「长什么样、按什么规则、效果由哪些数决定、还缺我哪些决定」，不用打开别的文档；调整阶段从「关键改动」能看到每一次影响效果的改动。

## 2. 设计

### 2.1 要解决的问题

替你和 AI 维护每个功能的一份「人看得懂、和代码同步、展示决定效果的关键设计」的文档。现在你要翻 7 份长文档，还常读到过期内容。

### 2.2 定位与边界

**定位**：每个功能一份给人看的需求设计文档。像一个会画图的产品搭档——把「长什么样、按什么规则跑、效果由哪些数决定、还缺你哪些决定」讲透：先放图，再用一两行字注释，不把长文档换个说法再讲一遍。

**核心立场**：读者是要拍板、注意力有限的人。所以只写当前设计里决定九成效果的内容，按固定顺序、按需取舍；每一项先图后字；历史只留末尾 15 条关键改动；凡是会改变效果的改动，都要在这份文档里留下痕迹。

**范围**：一个功能，包括它在各个阶段的迭代。做四件事：新建、按阶段更新、出图、上线前检查。

**不处理**

| 不处理 | 交给 |
|---|---|
| 写给 AI 的 PRD、feature-spec | forge-prd |
| DESIGN.md 文字规格、token 表 | forge-design |
| 在真比例骨架上定布局、比例 | forge-design-lab |
| 写或改 prompt 本身 | prompt-craft |
| 写代码 | forge-eng（codex） |
| 进度和状态 | forge-status |
| 复盘 | forge-fupan |
| 对外文章、发布公告 | 不在范围 |

**很像但不该触发的话**
1. 「把 DESIGN.md 模块 28 的 token 表重新生成一下」→ forge-design-lab
2. 「AI 搜索现在做到哪了，还有什么没做」→ forge-status
3. 「帮我写一份 XX 的 PRD」→ forge-prd
4. 「给 AI 搜索写一篇对外介绍文章」→ 不触发
5. 「复盘一下这次迭代」→ forge-fupan
6. 「这个总结 prompt 效果不好，帮我改」→ prompt-craft（改完后再由本 skill 更新文档）

### 2.3 触发与分流

**应该触发**：「给 XX 出一份需求设计文档」「PRD 太长我看不懂，整理成我能看的」「更新一下 AI 搜索的设计文档」「设计文档的截图过期了，重拍」「上线前检查一下设计文档跟上没有」「新需求，先建设计文档」，以及 forge 各阶段收尾时的调用。

**进来之后怎么走**

| 意图 | 判断信号 | 怎么做 |
|---|---|---|
| 新建 | `docs/modules/<功能>.md` 不存在 | 按需求类型选项目 → 写骨架、填已知信息 → 画示意图 → 检查 → 打开给你 |
| 阶段更新 | 文档已存在，且来自某阶段收尾或你说「更新」 | 只改受影响的部分 → 重出相关的图 → 关键改动加一行 → 检查 → 对话里三行汇报 |
| 出图 | 「截图」「示意图」「重拍」 | 跑出图脚本 |
| 检查 | 「上线前」「检查」，或 forge-review / forge-ship 调用 | 跑检查脚本 → 报告 |
| 潜在 | 你抱怨「文档太长看不懂」「调整看不到」 | 一句话说明 + 问要不要建 |

### 2.4 产出框架

**文档的固定顺序**（不适用的项目略去，顺序不变）

| # | 部分 | 什么时候写 | 首选形式 |
|---|---|---|---|
| 0 | 一句话 · 阶段 · ⚠️ 待你拍板 | 必有 | 清单（每条带建议） |
| 1 | 需求背景 | 必有 | 现状失败的例子（图或数字）+ 3 行字 |
| 2 | 目标与成功标准 | 必有 | 表：标准 / 怎么算达到 / 现在；加「不做」一行 |
| 3 | 用户流程 | 必有 | 流程图（主路径 + 岔路） |
| 4 | 页面布局 | 有界面 | 标注图（尺寸画在页面上） |
| 5 | 状态一览 | 有界面 | 状态缩略图 + 文案表 |
| 6 | 交互与细节 | 有界面 | 局部放大标注图，一张图一句话 |
| 7 | 业务规则 | 有后端 | 规则表，数值写死 |
| 8 | 召回 / 数据逻辑 | 有 AI 或算法 | 漏斗图，关键数字放大 |
| 9 | AI 生成（prompt） | 有 AI | 流程管道图 + 关键规则清单 |
| 10 | 效果样例与评估 | 有 AI | 真实输出截图 + 评估方法 |
| 11 | 成本与速度 | 有 AI 或重计算 | 一张小表 |
| 12 | 系统怎么搭 | 有后端 | 架构图 |
| 末 | 细节在哪 · 关键改动 | 必有 | 链接表 · 一行一条，最多 15 条 |

**每次运行后在对话里的汇报**：三行——改了哪几部分、关键改动加了哪一行、检查结果；如果待拍板有变化，再加一行。

模块多于 8 个，但这是你定的框架，而且按需求类型取舍后，一般只写 6–10 项。

### 2.5 执行流程

| 步 | 做什么 | 用什么 | 失败怎么办 |
|---|---|---|---|
| 1 | 读项目文档规则和已有资料（PRD、feature-spec、讨论稿） | 读文件 | 没有资料 → 只写背景、目标、待拍板，其余标 ⏳ |
| 2 | 判断需求类型，决定写哪几项 | 需求类型对照表 | 判断不了 → 问一句「有没有界面 / 有没有 AI」 |
| 3 | 写或改正文（只写现在，数值写死） | 文档模板 | — |
| 4 | 出图：示意图用 HTML 模板渲染；页面用骨架或真实截图加标注 | 出图脚本 | 没有本地服务 → 用骨架截图；没有 Playwright → 只出源文件 |
| 5 | 关键改动加一行，超过 15 条删最早的 | — | — |
| 6 | 跑检查 | 检查脚本 | 报错先怀疑脚本，在已知健康的文档上验证过再信 |
| 7 | 打开文档，在对话里三行汇报 | VS Code | — |

### 2.6 要带的资源

| 资源 | 放哪 | 为什么 |
|---|---|---|
| `render-diagrams.mjs`：HTML 示意图 → PNG | scripts/ | 每次都一样 |
| `check.mjs`：`watch` / 历史词 / 关键改动条数 / 图片存在 / 链接 | scripts/ | 上线前门禁 |
| `annotate.mjs`：截图标注工具（框、间距线、引线标注）+ 只放行 GET 的保险 | scripts/ | 每个项目的截图脚本都要用 |
| 示意图样式 + 5 种模板（现状、流程、漏斗、流程管道、架构） | assets/ | 会被复制进项目 |
| 文档骨架模板 | assets/ | 新建时复制 |
| 写法规则：ADHD 原则、13 项定义、每项怎么展示 | references/ | 写之前读 |
| 阶段对照：每个 forge 阶段填哪几项 | references/ | 阶段更新时读 |
| 范例：info2action AI 搜索 | references/ | 第一次在新项目用时读 |
| 踩坑：中文路径编码、git 路径转义、无头浏览器隐藏滚动条、写接口拦截、生产连接 | references/ | 写截图脚本前读 |

### 2.7 输入与输出

**真实会说的话**
1. 「AI 搜索的 PRD 和 DESIGN 太长了，帮我出一份我能看懂的设计文档，要能看到三栏布局和召回阈值」
2. 「新需求：精选页加一个按标签筛选，先建设计文档，还没有页面」
3. 「额度规则改成每人每天 2 次了，把 AI 搜索的设计文档更新一下」
4. 「设计文档里的截图还是旧的，重拍一下，记得别往生产库写东西」
5. 「准备上线了，检查下设计文档有没有跟上代码」
6. 「prompt 改到 v5.2 了，文档里 AI 生成那块同步一下」

**产出**：`docs/modules/<功能>.md` + `docs/assets/visuals/<功能>/overview/`（图片和 `src/` 源文件）+ 对话里三行汇报。

### 2.8 上下文分层

| 层 | 放什么 | 体量 |
|---|---|---|
| description | 触发场景、近似不触发的边界 | 约 300 字符 |
| SKILL.md | 定位、四种意图、执行流程、红线、汇报格式 | 目标 < 200 行 |
| references/ | 写法规则、阶段对照、范例、踩坑 | 各自点名何时读 |
| scripts/ | 出图、标注、检查 | 不进上下文 |
| assets/ | 模板 | 复制进项目 |
