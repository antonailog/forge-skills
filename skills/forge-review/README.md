# forge-review

上线前的结构性审查

## 要解决的问题

测试全绿的分支，照样可能带着结构性问题上线：批量更新漏了 WHERE、先读后写有竞态、LLM 输出不经校验就写进数据库、新增的枚举值在 diff 以外的文件里没人处理。这类问题测试通常抓不到，要对着 diff 一类一类查。审查如果只出一份问题清单，后面还得有人逐条去改。

## 运行方式

![forge-review 结构图](../../docs/diagrams/forge-review.jpg)

读完整个 diff 再开始评论，没有 diff 就停。两轮审查的发现分两路处理：机械、无争议的直接改，逐条列出改了什么；有取舍的攒成一批问用户，用户选按建议修或跳过。收尾对照 TODOS 和项目文档，标出这次改动解决了哪些条目、让哪些文档过时，然后交给 forge-ship，自己不提交。

## 关键设计

一次上线前审查要同时做到两件事：查出测试跑绿也会漏掉的结构性问题，查出来的每个问题当场有处理。forge-review 以基础分支到当前分支的完整 diff 为起点，把检查项分成十类、两轮：第一轮查四类严重问题，第二轮查六类信息性问题，每条发现都写明文件、行号、问题和修法。

- **严重级留给测试抓不到的问题**：第一轮只查 SQL 与数据安全、竞态与并发、LLM 输出信任边界、枚举与值完整性四类，比如软删除的记录没在所有查询里过滤、状态转换只靠应用层检查、Prompt 里带了密钥。条件副作用、魔法数字、死代码、测试缺口、前端转义、设计值越界放第二轮。每类的检查点都列在 `SKILL.md`。
- **枚举完整性要读到 diff 之外**：diff 新增枚举值、状态或类型时，在全仓搜出所有引用同级值的文件，逐个读，确认新值在每一处都有处理（`SKILL.md`）。
- **每个发现都配一个动作**：机械、无争议的直接改，比如补上无歧义的 WHERE 条件、去掉 outline: none 和 !important、修 HTML 转义，每条写明改了哪一行；有取舍的攒进一次提问，每条附建议修法和推荐，用户选按建议修或跳过（`SKILL.md`）。
- **设计文档没跟上代码记为严重**：项目有需求设计文档检查脚本时，审查会运行它，不通过就记为严重发现，修法是调用 forge-feature-doc 更新文档；读者拍板看的是文档，文档过期就会按过期的设计拍板（`SKILL.md`）。

```text
forge-review/
└── SKILL.md   十类检查清单、两轮审查、修复与提问格式
```

## 其他

- 不处理：提交和发布（交 forge-ship）；用户点名 `/code-review` 或 `/verify` 时用对应的内置 Skill
- 前提：git 仓库；装了 `gh` 时从 PR 或仓库设置读基础分支，读不到回退 main
- 注意：第 10 类「设计值越界」只在仓库有设计零件库时才查，且只查本分支新增的行；越界的值要么改用模板值，要么由用户确认登记为定制，不准为过检查加豁免注释
