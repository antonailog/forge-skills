# forge-bugfix

一次修一个：先根因，再写代码

## 要解决的问题

跟 AI 说一句「这里有问题」，它常常跳过根因直接改，结果修一个冒一个。让它一个会话包下所有报上来的 bug，修的过程中又会吸进新 bug 和新需求，几个 bug 的上下文互相污染：这个 Skill 的早期版本就这样失控过，一个会话做成 21 个提交、9 个 bug、1.8M tokens 的小型重构。修完由 AI 自己判断「好了」，用户也说不清什么时候算修完。

## 运行方式

![forge-bugfix 结构图](../../docs/diagrams/forge-bugfix.jpg)

P0—P1 每个会话只做一次：巡检并行会话、读 PRD 和 bug 历史、回放教训账本。之后每个 bug 走一轮：用户确认范围后建 BF 报告和独立 worktree，根因和修复方案也要用户确认才动手；forge-qa 自动验收不过就回 P5 重修，连挂 3 次交给用户判断。QA 全过之后，用户在报告里填最终结论，Pass 才合并，Fail 回 P5 只修原 bug。

## 关键设计

- **不做根因分析就不写修复代码**：先复现，再用带编号的临时日志逐个验证假设，用 5 Whys 讲清根因和方案，用户确认后才改；3 个假设都失败就停下来质疑架构，不硬修
- **一次只修一个 bug，每个 bug 独立 worktree**：确认共因的最多两个一起修，下一个 bug 默认开新会话；代价是每次要重读项目文档，换来干净的上下文和清楚的边界
- **新发现不顺手修**：原 bug 没通过前，新问题只记为待确认；通过后先告诉用户「这个 bug 已完成」，再问要不要写进 backlog，新问题可能只是随口一提，入档会影响后面的优先级
- **声称「同根」必须举证**：要拿出同一函数、同一状态字段或同一上游依赖的具体位置，证据不足按独立 bug 处理；AI 爱把看起来相关的 bug 说成共因一起修，结果改动面变大，其中一个还没修好
- **QA 全过也不自动合并**：BF 报告先过校验脚本，查截图、断言和前后端进程身份，再由用户填 Pass / Fail / Pass + 新发现；接口返回 200、单测通过、没有 console error 都只是证据，不等于用户遇到的问题已经解决

## 其他

- 不处理：新需求（进 backlog，建议走 forge-prd）；同类问题的全库扫描（交 forge-review）
- 前提：git 仓库；P6 用 Skill 工具调 forge-qa；在 Claude Code 里用时，修复代码经 codex-delegate 派给本机 Codex 写，Claude 验收后提交
- 注意：多个窗口同时修 bug，靠 `.forge/active.md` 登记和功能域判重防撞车，合并前先跑 `git merge --no-commit --no-ff` 预演
- 注意：worktree 里要启动应用时，走项目统一的 dev 入口，验收地址必须能追溯到当前 worktree 的进程
