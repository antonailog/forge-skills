# forge-ship

建 PR、合并、同步主分支

## 要解决的问题

「合并了」可以指代码已提交、PR 已合并、本地 main 已同步，也常被听成线上已更新。发布流程只做到建 PR、汇报又不把这几层分开，用户就得反复追问本地合并、远程 PR 和服务器部署各做到了哪一步。合并、部署、删远程分支这类仓库外操作，走到哪一步才撞上权限门，发布就在哪一步停下来等授权。

## 运行方式

![forge-ship 结构图](../../docs/diagrams/forge-ship.jpg)

先按用户的说法定模式：说「发 PR」走 PR only，建完 PR 就停；说「发布」「合并」走 Full ship，一路合并 PR，再把本地基础分支快进到远程。仓库外的写操作开工时一次列清单请用户授权；测试失败、合并冲突、PR checks 不过都会停下，不绕过。最后的总结拆成七格逐项报状态，没部署就写明没部署。

## 关键设计

一次发布要同时做到两件事：代码按仓库的保护规则走到该到的那一层，汇报时每一层做到哪一步都说得清。forge-ship 把发布排成一串固定步骤：安全检查、同步基础分支、测试、diff 审查、提交推送、建 PR，Full ship 再接合并和本地同步；每一层都有自己的停止条件，碰到就停在这一层。

- **每一层做到哪步，凭证据报**：发布总结按模式、提交、PR 状态、远程基础分支、本地基础分支、测试、CHANGELOG、部署分格填写。合并后记下远程基础分支的新提交号，本地和远程指向同一提交才写已同步，PR 没配远程检查只写「无远程 checks」（`SKILL.md`、`references/merge-and-sync.md`）。
- **本地基础分支只从远程快进**：同步前先查本地基础分支所在的 worktree 是否干净、和 origin 有没有分叉，干净且能快进才执行快进合并；有未提交文件或分叉就停下问用户，用户选暂存时用带名字的 stash，同步后由用户决定何时恢复（`references/merge-and-sync.md`）。
- **测试命令要让失败如实暴露**：测试命令取项目 CLAUDE.md 或验证脚本里记录的那条，单独执行；失败先判断和本次改动有没有关系，相关就修了重跑，无关就列出证据问用户要不要继续。项目有需求设计文档检查脚本时也在这一步跑，不通过先更新文档（`SKILL.md`）。
- **仓库外的写操作开工前一次授权**：动作对象不在本仓库工作区里就算仓库外写操作，比如合并自己的 PR、删远程分支、部署、改数据库、写第三方账号。开工时一次列清单请用户点名授权，同时给出可以预置进本地权限配置的允许规则，由用户亲手加；中途被拦就换路（`SKILL.md`）。
- **推送前把整个 diff 再看一遍**：查调试代码、密钥和私有配置、误提交的构建产物和缓存、无关文件，以及数据库、prompt、Skill、部署脚本这类高风险改动；推送被拒先看远端差异，再请用户选 rebase 或 merge（`SKILL.md`）。

```text
forge-ship/
├── SKILL.md                两种模式、发布步骤、总结表格式
└── references/
    └── merge-and-sync.md   合并前检查、合并 PR、同步本地基础分支
```

## 其他

- 不处理：代码审查，默认先走 forge-review 再 ship
- 前提：`gh` 已登录，建 PR、查 checks、合并都靠它
- 注意：当前分支就是基础分支时不会直接 ship，先问要不要新建功能分支
- 注意：Full ship 找不到本地基础分支的 worktree 时只报告，不自动创建
