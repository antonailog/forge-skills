# forge-ship

建 PR、合并、同步主分支

## 要解决的问题

「合并了」可以指代码已提交、PR 已合并、本地 main 已同步，也常被听成线上已更新。这个 Skill 的前身只覆盖到建 PR；一次发布中，用户反复追问本地合并、远程 PR 和服务器部署有什么区别，原流程没把这几层分开，答不清每层做到了哪一步。合并、部署、删远程分支这类仓库外操作，每次临时撞权限门，同类问题在教训账本里复发了 5 次。

## 运行方式

![forge-ship 结构图](../../docs/diagrams/forge-ship.jpg)

先按用户的说法定模式：说「发 PR」走 PR only，建完 PR 就停；说「发布」「合并」走 Full ship，一路合并 PR，再把本地基础分支快进到远程。仓库外的写操作开工时一次列清单请用户授权；测试失败、合并冲突、PR checks 不过都会停下，不绕过。最后的总结拆成七格逐项报状态，没部署就写明没部署。

## 关键设计

- **发布不等于部署**：总结里提交、推送、建 PR、合并、远程 main、本地 main、部署七种状态分开报；每层的证据不同，没执行部署并验证运行态，就写「线上部署未执行」
- **本地 main 只从 origin 快进**：不用功能分支直接覆盖本地 main，工作区脏了或分叉了就停下问，禁用 `git reset --hard`；用户没提交的文件不能被静默覆盖
- **不用会吞失败的链式测试命令**：`npm test || yarn test || echo "未找到测试命令"` 这种写法，测试挂了整条命令照样成功；优先跑项目里记录过的测试命令，失败了先判断和这次改动有没有关系
- **仓库外写面开工前一次授权**：部署、数据库写入、第三方账号写入、合并自己的 PR，一次列清单请用户点名授权，并给出可以预置的 allow 规则；AI 代改权限配置会被拦，这几条只能用户亲手加，被拦就换路，不原样重试
- **checks 为空不说 CI 通过**：PR 没配远程 checks，只能报「无远程 checks」

## 其他

- 不处理：代码审查，默认先走 forge-review 再 ship
- 前提：`gh` 已登录，建 PR、查 checks、合并都靠它
- 注意：当前分支就是基础分支时不会直接 ship，先问要不要新建功能分支
- 注意：Full ship 找不到本地基础分支的 worktree 时只报告，不自动创建
