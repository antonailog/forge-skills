# 一、工作总结：怎么写

六块：摘要、过程回顾、关键决策、结果评估、交付物、遗留事项。承担「回顾」和「速查」：读者 3 秒认出这是哪一次，10 秒知道结果，下次接着做时一眼知道剩什么。

写之前手上要有：会话摘要（digest.py 的输出）、`git status` / `git log` 看提交状态、写过的文件清单（摘要末尾那张表）。

## 摘要（最后写）

其余各块都写完再写摘要，它是从过程回顾和结果评估里提出来的。

- **标题**：一句结论。主语是交付物或决定，谓语是结果（「博客全站和活动页有了每小时更新的访问看板」）。不写「××复盘」「关于××」
- **状态**：已上线（成果已经在真实环境生效：网站上线、邮件按新办法发出、代码合并发布；还没验收完的子目标在结果评估里标「待验证」）· 进行中（还有主目标没做完，或停在等用户决定）· 仅讨论（没有改动任何产物）
- **why / did / got**：起因、做法、结果三句（STAR）。汇总页列表显示两行：第一行 why → did（灰），第二行 got（正文色，数字加重）；单篇页顶部分起因、做法、结果三栏，原话 cause 放在起因栏下
  - why：为什么要做，10–25 字，大白话（「想知道网站和活动页有多少人看、多少人订阅」）
  - did：做了什么、关键怎么做，15–35 字（「写了收数脚本和两个看板，放在博客域名下每小时更新」）
  - got：结果，带数字或明确状态，15–45 字；结果评估里影响最大的一条未达成放这里（「全站 209 访客、活动页约 130、订阅 2；61% 来源识别不了」）
  - why 和 did 合起来不超过 60 字；不写文件名、内部编号
- **cause**：用户提出需求的第一句原话
- **projects / module**：归档位置。项目名先看 `记录/复盘/` 下已有的文件夹，有就沿用；没有用工作区里的项目文件夹名。模块名按顺序找：这个项目下已有的模块文件夹 → 项目文档里现在的叫法（project.md 的模块表、各模块的规则文件，以最近改过的为准）→ 都没有就用这次做的功能名（2–6 字的名词，如「每日简报」）。模块后来改过名的用现在的名字，会话时的叫法可以留在标题里。一篇跨两个项目，两个都写，文件夹放在第一个下面

## 过程回顾

全篇的坐标：分几个阶段、每段从哪开始、经过了什么、产出了什么。

- **切分**：只按用户的需求转折切——提出新目标（包括回答选择题时顺带提的新要求）、改变方向、叫停、要求上线发布。只回答选择题、说「好」「可以」继续的不切；两个转折相隔不到 10 分钟的合并成一段；时间空档本身不是边界，上下文压缩也不是。一般 3–6 段
- **每段写**：开始时间（北京时间）、耗时（跨夜写「跨夜」）、阶段名（名词短语）、触发原话（超过 40 字截断加「…」）、经过 2–3 句（做了什么、遇到什么、怎么处理，带关键数字）、产出（名词）、挂在这段的决策编号

## 关键决策

定过的事不再重复讨论；能看出现在的结果是哪个决定造成的。

- **收什么**：存在备选方案、且影响结果的决策。实现细节（变量名、用哪个库函数）不收
- **决策来源**，按顺序判定，命中第一条就停：
  1. 方案最早由用户提出，不在 AI 给的选项里 → 用户方案
  2. AI 列了选项没推荐，用户选定 → 用户选择
  3. 用户只表达偏好没拍板，AI 照此执行 → 用户倾向
  4. AI 给了推荐：用户选了推荐项 → 采纳建议；改了一部分 → 调整建议；选了别的或拒绝 → 否决建议
  5. 用户没参与 → AI 决定：会话里写明过的记「AI 决定 · 已告知」，没写过的记「AI 决定 · 未告知」

  常见的拿不准：用户挑了 AI 做出来、但不在选项里的版本 → 用户方案；AI 写了带条件的计划（「无图进收件箱我就改外链」），用户只回了条件的结果、没反对 → 采纳建议；AI 给了默认、用户回复时跳过了这一条 → AI 决定 · 已告知
  依据是建议采纳研究里的 Judge-Advisor System 和 Sheridan 的自动化等级；「否决建议」和「未告知」最值得回看，页面上单独着色
- **备选方案**只写会话里出现过的（AI 列的选项、讨论过的做法）；AI 没告知就定的，可以写一个常见做法并注明「会话里没提」
- **理由**只摘原文，不用「」括起来（决策来源一栏已经说明是谁的话）；用户没说写「未说明」；AI 的理由开头写「AI 推荐理由：」
- **后果**只写会话里已经看到的，没看到写「—」

## 结果评估

这次要达成哪些目标，每一项做到没有、证据是什么；没做到的是取舍、执行问题，还是没做完。

- **目标树**：主目标（通常 1 个）→ 子目标（每个能单独验证，2–5 个，各有完成标准）；衍生目标单列，`origin` 写起因：新增需求、过程发现、审查发现
- **目标名**：改写后的标题，「对象 + 要达到的状态」，14 字以内。不用原话，不写动作（✗「做一个看板」 ✓「活动页访问效果可随时查看」）
- **状态**：达成 · 部分达成 · 待验证（交付了，要等数据确认）· 未达成 · 移出范围（evidence 里链到决策「（D5）」）· 延后（同步写进遗留事项）
- **父目标怎么汇总**（不计移出范围的子目标，按顺序判，命中就停）：全部达成 → 达成；只有达成和待验证 → 待验证；全部延后 → 延后；有达成或待验证、也有未达成或延后 → 部分达成；其余 → 未达成
- **evidence**：数字、截止时间、验收结果，取自会话原文
- **findings**：附带发现，会话里看到、但不属于任何目标的事实，一条一句

## 交付物

这次做出了什么效果、效果由哪几样东西决定。线上的一点就开，本地的一点就能看内容，代码能顺着讲解学到写法。四类：

**结果**：能直接看、直接用的成品。名称、网址、访问条件（要登录写「需密码」，不写账号密码）、一句 meta。公开页面 `shot: "capture"` 截图；没有网址的成果（发出去的邮件、本地生成的文件）写 `file`，本地 html 也能 `capture`；被新版替代的标 `stale: true`。线上页面会后又被改过的，截图优先用会话里读过的那张（JSONL 里的图片可以抽出来存成文件），meta 里写清是哪个时间的样子。

**关键文件**：不是代码，但改了它效果就变（prompt、规则、配置），或是这次主要的文字产出。起一个 10 字内的功能名（title）；配置拆出设定值（value，加粗显示）和关键行（marks / match）；文档写一句说明。

**关键代码**：承担主要逻辑的文件，按模块分组。
- 模块：分工（role，一句）+ 关键做法（practices：标准叫法 + 解决什么）
- 每个文件：功能名（title，10 字内）、一句说明（detail，卡片上显示）、讲解：负责什么（role）、技术栈（stack）、输入 → 输出（io）、执行流程（flow：每步一句，挂函数名，行号交给 build.py 算）、设计理念（ideas，2–4 条）
- 讲解里每个说法逐条对照代码核实：读了那段代码再写，不凭会话里 AI 当时的描述
- 文件会后又改过的，讲解按现在的文件写——页面里嵌的、行号算的都是现在的内容，抽屉会标出「会话结束后又改过」
- 模块之间怎么串，画一张 Mermaid 流程图放 `code.flow`

**其余产出**：部署运维、第三方库、本地预览、文档同步，按组列，每行写用途和改动量（`git diff --stat` 拿得到就写行数，拿不到写「改 N 处」）；改了服务器（nginx、systemd、定时任务）单列在 `server`。

规则：新增的文件不标，改已有文件的标「修改」（看摘要文件表里第一次是「改」还是「写」，拿不准用 `git log --diff-filter=A -- <文件>` 查）；含访客 IP、日志原文这类隐私的文件不列；会话结束后删掉的标「已删除」。

## 遗留事项

下次接着做时，一眼知道还剩什么、谁来动、从哪句话开始。

- 找出这次会话里冒出来、到结束时没收尾的事（会话之前就有的老待办不收，除非这次动过它），每条定归属：decide（待你决定）· wait（等条件）· ai（AI 来做）
- AI 提过、用户没回应的提议算待你决定；提交、推送、部署这类要用户开口的也算
- 每条都写 `when`：等条件的写清等什么、什么时候能做；待你决定和 AI 来做的写「随时」
- `prompt` 写一句能直接复制给 AI 的话，带上对象和验收方式
- `status` 链上项目的最新状态文件（project.md 或 todo.md）
- `asOf` 写「截至 11-04 12:15」
