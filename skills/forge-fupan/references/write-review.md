# 二、工作复盘：怎么写

两块：对标分析、需求表达。主线：看清这次和最佳路径差在哪 → 下次能用关键词说出来 → 自己能判断方向对不对。

## 对标分析

把这次工作的关键环节，和这类活的业内做法一步步对照。页面上画成一条路线：最佳路径的每一步是一个节点，按判断着色，点开看本次 ⇄ 行业差在哪。

### 先定最佳路径

1. **列这类活的业内做法**：先写你自己知道的通用流程（这类工作一般分几步、每步要定什么），再联网核对。哪些要联网：变化快的知识（模型评测、官方使用指南、Cookbook、System Card、新工具的能力边界）必须查；稳定的知识（React 是什么、HTTP 基本认证）不必。查到的和你自己的判断互相校验，对不上的以有出处的为准
2. **定顺序**：对标项按业内建议的先后排成 `path`。会话 A 按 Amplitude 数据规划的顺序：先定指标口径，再选工具、实现、上线
3. **这类活没有公认流程的**（一次性的排查、纯讨论）：不硬凑路线，只挑 3–5 个关键做法逐个对照，`path` 按判断排（缺失 → 待改进 → 合理偏离 → 一致）

### 每个对标项

| 字段 | 写法 |
| --- | --- |
| `id` | 短 id（b1、b2……），`path` 按它排顺序 |
| `step` | 最佳路径上「该做什么」，名词短语（「统计方案选型」「指标口径」） |
| `eval` | 差距分析的四级：一致（和业内做法一样）· 合理偏离（不一样，但有约束撑着、代价可接受）· 待改进（不一样，也没有好理由）· 缺失（这步没做） |
| `gapLine` | 一句话差距，读者只看这句也知道差在哪 |
| `mineKw` / `baseKw` | 本次的关键词 ⇄ 行业的关键词，各 2–5 个；只放有指向性的词（见 write-knowledge.md「关键术语」的标准），实现细节（具体 API、状态码、函数名）不放 |
| `dims` | 逐维对比：维度名 + 本次一组词 + 行业一组词 + 是否相同；只列不同的，相同的最多留一两条做对照 |
| `why` / `cost` | 为什么这样做（会话里的约束和理由）、代价是什么 |
| `say` | 下次这样说：用关键词写好的一句指令，能直接复制给 AI |
| `keywords` | 这一步涉及的术语：一句话说能做到什么、本次还是行业、外部链接 |
| `evidence` | 会话证据：原话（带引号）、数字、AI 当时的选项 |
| `sources` | 这一步引用的来源键（必填，指向 `review.sources`；没有引用写空列表） |
| `landscape` / `axes` | 选型类才写：可选方案按两个维度摆开（0–100），本次的选择 `chosen: true`；`axes` 写两条轴的名字（x 左→右、y 下→上），没有就不标轴 |

判断写「一致」的也要写：路线上要看得出哪几步做对了。

### 链接

工具、做法、名词都配外部链接，放进 `review.sources`。每个链接都要打开核对：能打开，`note` 写的意思原文里确实有（抓取工具给的是转述，意思对得上就算；note 写意思，不加引号冒充原文）。打不开或找不到的换来源；官方原文抓不到时可以用可靠的转载或镜像，note 里写明「转载」；找不到可靠来源的词不挂链接。优先官方文档和有名的一手资料（厂商文档、标准、知名团队的工程博客）。

## 需求表达

整份复盘里唯一讲用户自己的内容：他这次的原话和更好的说法差在哪，复习时练「说得出」。

- **收什么**：只收用户的表达问题。判据：同样一句话交给一个称职的人类执行者，他也会理解错 → 算用户的；不会 → 算 AI 的，不收（例：AI 没问就直接开工、做到一半又停下来讨论，是 AI 的问题）
- **怎么分**：按问题类型，类型用需求质量的标准叫法（ISO/IEC/IEEE 29148）：需求不完整（缺了在哪、给谁、多久、做到什么程度）· 需求不可验证（没说怎么算做完）· 需求有歧义（一句话两种读法）· 需求不一致（前后说法冲突）· 约束缺失（没说不能动什么）· 优先级缺失。一句话的问题和多次出现的习惯都按类型归
- **每条写**：类型 → 一句标题（「没说在哪看、多久看、谁能看」）→ 原话（北京时间 + 原文，多次出现就列多条）→ 造成了什么（会话里实际多花的轮次、返工）→ 下次这样说（把缺的补上，一句能直接用的话）
- 没有就整节不写，不为凑数降低标准；AI 自己的偏差不收

## 认领经验（review.sops）

经验库是一份份任务级的 SOP（「给网站加访问统计」「定页面视觉方向」……），每份分几步，每步有一句「历史相关」：用户以前做这一步时的真事。写复盘时把这次的真事挂上去，经验库就跟着长。

1. `build.py --catalog` 列出全部经验和它们的步骤
2. 这次做的事对应哪份就认领哪份，可以几份；只认真对得上的，宁缺毋滥
3. 每份写这次做到了哪几步：`{"sop": "S02", "steps": [{"step": "s1", "eval": "待改进", "note": "访问看板没先写追踪方案，口径改了 5 次，访客数先后出现 120–150、116、133 几种说法。"}]}`
   - `eval` 和对标分析同一套四级；这一步在对标分析里有对应项就沿用它的判断
   - `note` 一句话讲当时情况、怎么做的、结果如何，60 字内（不算空格）、最多一个句号，事实只取会话原文；数字照原文写阿拉伯数字，数字、英文和中文之间留一个空格
4. 对不上任何一份的，写进 `review.sopCandidates`：`{"name": "这次做的事（动宾短语）", "why": "为什么现有经验都对不上"}`。同类攒到 3 篇，用户说「整理经验」时再写成新的一份（整理不在复盘里做）

build.py 会把这篇加进那份经验底部的列表，认领的步骤换成这次的一句：几篇认领同一步时，显示工作开始最晚的那篇；那篇后来不认领了，换回下一篇的。同一篇改了认领再重跑，上次写进去的会先撤掉。同一步在一份认领里只写一次。

## 写完自查

- 每个对标项的 `say` 都用上了 `baseKw` 里的词
- 「待改进」「缺失」的项，在遗留事项或知识拓展里有下文（要么列成事要做，要么作为盲区补知识）
- 需求表达的每条原话都能在会话摘要里搜到
