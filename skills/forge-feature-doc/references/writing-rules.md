# 写法规则

目录：读者与判据 · 按类型取舍 · 12 个部分怎么写 · ADHD 写法 · 只写现在 · 待拍板 · 关键改动 · 链接 · 篇幅

## 读者与判据

读者是要拍板、注意力有限的人。他打开这份文档，要在 10 分钟内回答四个问题：这个功能长什么样？按什么规则跑？效果由哪些数决定？还缺我哪些决定？答不出其中任何一个，文档就没写到位；需要他再去翻 PRD、DESIGN 才答得出，也算没写到位。

**放不放**：问一句「改了它，用户能感知到、成本会变，或者对错会变吗？」会，就进正文，并且把数值写死；不会（字段名、样式选择器、建索引语句、全部 token、测试清单），就放进「细节在哪」链接到的文档。

## 按类型取舍

| 部分 | 必有 | 有界面 | 有后端 | 有 AI 或算法 |
|---|---|---|---|---|
| 待你拍板、1 背景、2 目标、3 流程、细节在哪、关键改动 | ✓ | | | |
| 4 布局、5 状态、6 交互与细节 | | ✓ | | |
| 7 业务规则、12 系统 | | | ✓ | |
| 8 召回 / 数据逻辑、9 AI 生成、10 效果样例与评估、11 成本与速度 | | | | ✓ |

不适用的部分整节删掉，编号保持原样（读者靠编号定位，跳号比改号好认）。部分名可以换成这个功能的读者熟悉的说法，比如筛选类功能把 8 叫「筛选漏斗」；编号和顺序不变。没有界面的纯后端需求，通常写 6–8 部分；完整的 AI 页面功能写满 12 部分。

## 12 个部分怎么写

每部分**先放图或表**，文字不超过 3 行。数字标在图上，正文里不再重复。

| 部分 | 回答什么 | 首选形式 | 常见错误 |
|---|---|---|---|
| 待你拍板 | 还缺读者哪些决定 | 编号清单：⚠️ **短标题**：现状一句。建议：一句 | 只列问题不给建议；把已定的事也列进来；满是正文才解释的术语，读者要先读完全文才看得懂 |
| 1 需求背景 | 谁、什么场景、现在哪里不好 | 现状失败的例子（截图或数字卡片）+ 「谁 / 场景」两行；已上线的功能写「不这样做会怎样」 | 写成产品愿景；没有具体的失败例子；写成「原来……后来……」 |
| 2 目标与成功标准 | 做到什么算好、不做什么 | 表：标准 / 怎么算达到 / 现在；表下一行「不做：…」 | 标准写成形容词（「体验好」）；漏写成本和效果评估 |
| 3 用户流程 | 从进入到拿到结果怎么走、哪里会出岔子 | 流程图：一行主路径 + 一行岔路，岔路标「在第几步」 | 只画主路径；把系统内部步骤画进用户流程 |
| 4 页面布局 | 分几块、什么比例 | 页面标注图：尺寸、间距、对齐线画在真实页面或骨架上；两者都没有时画页面示意（真实文案 + 区域编号）+「编号 / 区域 / 说明」表 | 用文字写「三栏、7:3」；比例来自想象而不是实测；画成只有方框和尺寸的抽象线框 |
| 5 状态一览 | 每种情况长什么样、说什么话 | 状态缩略图两列表格 + 文案表（情况 / 文案 / 附带行为） | 只截正常态；文案只写在代码里 |
| 6 交互与细节 | 点了、滚了、输入时会怎样；影响观感的细节 | 局部放大标注图，两列表格，一图一句；纯行为（回车提交等）用 ≤3 行列表 | 一张大图标十几处；细节只写不画 |
| 7 业务规则 | 谁能用、能用多少、怎么计 | 规则表（规则 / 现在），数值写死 | 规则散在各处；没写「什么算一次」这类口径 |
| 8 召回 / 数据逻辑 | 从哪找、找多少、门槛和排序 | 漏斗图：范围 → 各路 → 合并 → 取前 N，关键数字放大；筛选类功能用这张图把第 7 部分的规则串起来，不再逐条解释 | 只写「向量检索」不写阈值和条数 |
| 9 AI 生成 | 用什么模型、prompt 决定质量的几条规则、生成后怎么处理 | 管道图（输入 → 模型 → 输出 → 校验）+ 关键规则编号清单（≤10 条）+ prompt 文件链接；打分、分级类 prompt 再加一张「维度 × 档位」速查表，每格一个短语 | 贴 prompt 全文；只写模型名不写参数；打分 prompt 只列规则、看不出每档什么样 |
| 10 效果样例与评估 | 好的结果长什么样、怎么判断变好变坏 | 真实输出截图 + 样例数据一行 + 评估方法（没有就 ⚠️） | 用编造的样例；没有评估方法也不标 |
| 11 成本与速度 | 一次多少钱、多慢、能扛多少 | 小表：每次成本（含算法）/ 每天上限 / 用时 / 并发 | 只写单价不写日上限；用时只写平均 |
| 12 系统怎么搭 | 前后端和数据怎么连 | 架构图（一张）+ 已接受的风险一行 | 画成工程图（类名、函数名）；写接口字段 |
| 细节在哪 | 要看细节去哪 | 链接表（想看 / 去哪） | 写成纯文本路径，点不开 |
| 关键改动 | 最近改了什么影响效果的东西 | 表（日期 / 部分 / 旧 → 新 / 为什么），最新在上，≤15 条 | 写成流水账；记纯重构和补测试 |

## ADHD 写法

| 规则 | 为什么 |
|---|---|
| 开头先给一句话、阶段、待拍板 | 读者先知道「这是什么、我要做什么」，才有动力往下读 |
| 每部分先图或表，文字不超过 3 行 | 图一眼能看完；大段文字读者会跳过，跳过的部分等于没写 |
| 每条一行，加粗开头 | 扫一眼加粗词就能找到要看的那条 |
| 数值写死（「每人每天 2 次」，不写「少量」） | 形容词没法拍板，也没法和代码核对 |
| 理由最多半句 | 理由是帮读者判断对不对的，不是论证；长论证去讨论稿 |
| 只标例外：⚠️ 待拍板、⏳ 已定未做完 | 满篇标记等于没有标记；不标的默认已定且已实现 |
| 同一件事只在一处展开 | 两处展开就会出现两个说法，读者不知道信哪个。数值可以同时出现在图上和规则表里（都从代码取），解释和理由只写一处；待拍板引用数值，不展开 |

## 只写现在

正文描述当前设计，像在描述一个已经存在的东西。旧值、演变过程只进末尾的关键改动；更早的看 git。

不出现在正文里的词：改为、原来、之前、不再、新增、曾经、后来；日期（`2026-10-10` 这种）；版本号（prompt 版本号例外，因为它是当前值）。检查脚本会扫这些词。

数据的日期例外：实测数字要让读者知道新不新，写成「（实测 2026-08-02）」或「（数据 2026-08-02）」，检查脚本放行这两种写法。它标的是数据什么时候量的，不是设计什么时候改的。

| 不这样写 | 这样写 |
|---|---|
| 滚动条改为只在滚动时显示 | 滚动条只在用户滚动时显示 |
| 不再显示模型名 | 标题下只显示用时和引用条数 |
| v32.3 新增目录 | 宽屏左侧有目录 |

描述「刻意不做的事」可以用否定句（「没有『换一个问题』按钮」），它是当前设计的一部分；但别写成「去掉了……」。

## 待拍板

- 放在最前面，紧跟一句话和阶段。
- 每条：`⚠️ **短标题**：现状一句。建议：一句。`
- 每条要能单独读懂：读者此时还没看正文，现象和后果用他的话写，不用正文才解释的术语（实在要用，括号里半句解释）；末尾链到展开它的部分，如「（见 7 业务规则）」。
- 建议接受现状的小问题合并成一行：「两处我建议接受现状，你不回就按此：……」。
- 拍板后：把结论写进对应部分的正文，从待拍板删掉，在关键改动加一行。

## 关键改动

- 位置：文档最末，「细节在哪」之后。
- 一行一条：`| MM-DD | 部分（编号 + 名称） | 旧 → 新 | 为什么 |`，最新在上。
- 只记影响效果的改动：规则、文案、交互、布局比例、阈值、prompt、模型、架构。
- 最多 15 条；加第 16 条时删最早的。表头上方写一行「最近 15 条，最新在上；更早的看 git」。
- 新建时从 git log 和 CHANGELOG 里挑影响效果的改动补齐；理由查不到就写「理由未记录」，不替它编一个。

## 链接

- 文档里提到的文件都写成相对链接：`[prompt 全文](../../prompts/xxx.md)`。读者点开就能看，不用自己找路径。
- 不用绝对路径（`/Users/…`、`file://`）：只在写的人本机能点开，还把本机目录写进了仓库。检查脚本会拦。
- 路径里有中文或空格时用尖括号：`[配置指南](<../配置指南.md>)`。
- 图片用相对路径：`![布局](../assets/visuals/<短名>/overview/layout.png)`。
- 正文里不要用反引号写文件路径（`docs/xxx.md` 这种），检查脚本会提醒改成链接。

## 篇幅

- 正文（关键改动之前）10 分钟读完：中文约 4,000 字以内（按每分钟 400 字），不算图。
- 每部分不超过一屏（约 25 行 Markdown，表格行不算）；单张表超过 15 行就拆开，或把细节挪进「细节在哪」链接的文档。
- 超了先删再加：先删重复和理由，再把细节挪进「细节在哪」链接的文档。
