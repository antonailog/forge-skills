# 阶段对照：什么改动更新哪几部分

## 改动类型 → 要更新的部分

| 改了什么 | 更新哪几部分 | 要不要重出图 |
|---|---|---|
| 新需求 / 需求范围变了 | 一句话、待拍板、1 背景、2 目标、3 流程 | 现状图、流程图 |
| 业务规则（权限、额度、计数口径） | 7 规则；涉及用户可见变化的同步 5 状态、3 流程岔路 | 状态图、流程图 |
| 文案 | 5 状态的文案表 | 对应状态缩略图 |
| 交互（点击、滚动、输入、跳转） | 6 交互与细节；影响路径的同步 3 流程 | 对应细节图 |
| 布局比例、尺寸 | 4 布局 | 布局标注图、受影响的状态图 |
| 视觉细节（对齐、颜色、间距） | 6 交互与细节 | 对应细节图 |
| 召回阈值、条数、排序 | 8 召回；影响成本的同步 11 | 漏斗图 |
| prompt | 9 AI 生成（关键规则清单、版本号）；效果变化同步 10 | 管道图（如流程变了）、效果样例 |
| 模型、调用参数 | 9 AI 生成、11 成本与速度 | 管道图 |
| 架构、接口、任务调度 | 12 系统；影响规则的同步 7 | 架构图 |
| 待拍板有结论 | 结论写进对应部分，从待拍板删掉 | 按对应部分 |

每次都要做的：关键改动加一行；跑检查。

**不用更新**：纯重构、补测试、性能优化（不改变用户可见行为和成本）、把 bug 修回原设计。

## 各 forge 阶段做什么

| 阶段 | 调用时机 | 本 skill 做什么 | 图从哪来 |
|---|---|---|---|
| forge-brainstorm | 讨论收敛、准备进 PRD 时（可选） | 新建：只写背景、目标、待拍板 | 现状示意图 |
| forge-prd | PRD / feature-spec 定稿后 | 新建或更新：背景、目标、流程、规则、待拍板 | 现状图、流程图 |
| forge-design | DESIGN 定稿后 | 布局、状态、细节 | 设计稿或骨架截图；还没有就画线框 |
| forge-design-lab | 用户在工作台保存、按调整后的来时 | 布局、状态、细节 | 骨架页面截图加标注（骨架是 file:// 页面，标注工具同样能用） |
| prompt-craft | prompt 改完后 | AI 生成、效果样例 | 管道图、真实输出截图（有的话） |
| forge-eng | 实现完成、验证通过后 | 召回、成本、系统；页面图全部换成真实截图；去掉已做完的 ⏳ | 真实页面截图 |
| forge-bugfix | 修复改变了设计时 | 受影响的部分 + 关键改动 | 受影响的图 |
| forge-qa | 验收发现文档与实际不一致时 | 以实际为准更新，或把差异进待拍板 | — |
| forge-review | 上线前审查 | 跑检查；没通过就列为问题 | — |
| forge-ship | 合并、部署前 | 跑检查；没通过就拦下，用户明说跳过才放行 | — |

## 同一个提交

文档更新和它对应的功能改动放进同一个提交。检查脚本按「本分支里 `watch` 覆盖的文件改了、文档没改」报错，所以分开提交会在 review 时被拦。
