# forge-feature-doc

每个功能一份给人看的设计文档

## 要解决的问题

Forge 产出的 PRD、DESIGN、feature-spec 是写给 AI 执行的，篇幅必然长，一个项目的 DESIGN.md 有 9,582 行。要拍板的人读不完，迭代中改了交互、阈值、prompt 也看不到。文档和代码就一路漂移，一个功能一次审出约 100 处对不上。

## 运行方式

![forge-feature-doc 结构图](../../docs/diagrams/forge-feature-doc.jpg)

进来先分流：文档不存在就新建，各阶段收尾来的是更新，只改受影响的部分；用户只是抱怨看不懂时，问一句要不要建，不自动开工。新建和更新都以 check.mjs 收尾，被 forge-review、forge-ship 调用时它是上线门禁，没过就拦，用户明说跳过才放行。读者要做的决定集中在文档最前面的「待你拍板」，每条带建议。

## 关键设计

- **先图后字，每部分文字不超过 3 行**：读者是要拍板、注意力有限的人，大段文字会被跳过，跳过的等于没写
- **正文只写当前设计**：「改为、原来、不再」和日期不进正文，检查脚本会扫；旧值只进末尾的关键改动，最多 15 条
- **12 个部分是菜单，不是模板**：按有没有界面、后端、AI 取舍，不适用的整节删掉、编号不改，读者靠编号定位
- **文档和功能改动放进同一个提交**：分开提交，文档就会落后，漂移就是这么来的
- **截图只读，拦下所有非 GET 请求**：本地服务可能连着生产库、带着付费模型的 key；登录、额度、失败这些状态用拦截的假数据造

## 其他

- 前提：Node 跑脚本；出图和截图要 Playwright，没有时只交示意图的 HTML 源文件，说明图待补
- 注意：数值以代码和配置为准，对不上时改文档；只在生产环境变量里的值标「未核对生产」，不去读生产 .env
- 注意：scaffold 会把出图和检查脚本复制进项目，项目里没装这个 Skill 也能跑检查
