# forge-eng

写代码，在独立分支里做、先写测试

## 要解决的问题

让 AI 直接写代码，常见三个问题：还没跑验证就说「已修复」；先写实现再补测试，补的测试一跑就过，证明不了什么；多个会话在同一个目录改代码，互相冲突，开发服务抢端口，浏览器里看到的是旧代码。

## 运行方式

![forge-eng 结构图](../../docs/diagrams/forge-eng.jpg)

有 PRD 和 ENGINEERING.md 时默认走完整模式；小 demo 可选轻量模式，跳过文档和审查，worktree、TDD、验证门和原子提交照样保留。完整模式下四章审查每章停一次问用户，方案经用户拍板才建 worktree 开工。每个原子任务过了验证门才提交，修 3 次不过就停下报告；最后由用户选合并、提 PR、保留还是丢弃分支。

## 关键设计

工程实现要同时做到三件事：说完成时有证据，测试真能证明行为，几个会话并行时互不干扰。forge-eng 把一次实现拆成原子任务，按依赖分成几个 Wave 并行执行，每个任务过一道验证门再单独提交，全程在本会话独立的 worktree 里进行；`SKILL.md` 放流程骨架和三条铁律，每个环节的细则单独成篇，执行到那一步再读。

- **先有验证证据，再说完成**：每个任务提交前跑验证命令、读完整输出、看退出码，提交信息里写上验证结果，「应该可以」「可能修好了」这类说法禁用；同一个任务验证失败三次就停下，把试过的修法和最后的报错交给用户，一起看设计有没有根本问题。各类说法要什么证据、失败怎么处理，写在 `verification-checklist.md`。
- **测试力度跟着任务风险走**：后端逻辑、接口和 bug 修复走严格 TDD，先看到测试失败再写实现，先写了实现就删掉重来；前端组件补关键交互测试，样式、配置、文档不写测试；没有测试框架的项目，每个任务写一条可执行的验证命令。按文件类型自动定级的规则在 `tdd-guide.md`。
- **任务小到能单独验证、单独提交**：每个任务通常改 1—3 个文件，带 TDD 级别、验证命令和完成标准；互不依赖的任务放进同一个 Wave 并行，改同一文件的排到前后两个 Wave；每个任务一个提交，Wave 之间跑一遍全量测试（`wave-execution.md`）。
- **每个会话独占一个 worktree**：`worktree-guide.md` 管建 worktree、跑基线测试和分支收尾；`dev-environment.md` 规定开发服务由项目统一入口分配端口，测试地址从状态输出里读，收尾前停掉本 worktree 的服务。
- **能做完整版就做完整版，规模用阈值卡住**：完整方案只比捷径多几分钟时，推荐完整方案；动手前先做范围挑战，方案超过 8 个文件或引入 2 个以上新类、服务，就建议用户缩减范围（`SKILL.md` 第 1 步）。

```text
forge-eng/
├── SKILL.md                        流程骨架、三条铁律、分支收尾
└── references/                     执行到对应步骤再读
    ├── engineering-template.md     工程文档模板、四章审查细则
    ├── worktree-guide.md           建 worktree、基线测试、收尾
    ├── dev-environment.md          开发服务端口约定、测试框架检测
    ├── wave-execution.md           任务拆分、Wave 并行、原子提交
    ├── tdd-guide.md                TDD 分级、红绿循环、常见借口
    └── verification-checklist.md   验证门流程、证据对照、禁用说法
```
