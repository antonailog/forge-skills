# forge-brainstorm

头脑风暴：先挑战前提，再给 2—3 个方案

## 要解决的问题

想法还没想清楚就开始写需求，AI 往往顺着用户说「好主意」，照字面往下做，最后解决的可能是个错的问题。流程如果从写 PRD 开始，中间就没有讨论这一步。聊出来的结论只留在对话里，换个会话或换台电脑就接不上。

## 运行方式

![forge-brainstorm 结构图](../../docs/diagrams/forge-brainstorm.jpg)

产品、内容、构建、探索四种模式共用一条流程，差别在问哪套题、要不要搜外部现状、最后推荐去哪（见图下表）。用户拍板三次：确认模式、选定方案、确认思考文档，下一步去哪也由用户定；不想再被问时说一句「别问了」，直接出方案。

## 关键设计

一次头脑风暴要同时做到两件事：把问题本身问对，讨论出的结论换个会话还能接着用。forge-brainstorm 把对话约束和各阶段流程放在 `SKILL.md`，题库与反驳话术、思考文档模板各拆成一份参考文件；讨论收尾时落成一份按模板写的思考文档，下次会话从文档开头的续聊指引接上。

- **先质疑讨论的前提，再给方案**：出方案之前必问三个问题「这是正确的问题吗」「不做会怎样」「已有什么能复用」；在项目目录里会主动搜相关的已有资源。三问和配套的思维工具写在 `SKILL.md` 的前提挑战一节。
- **提问照原文问，一次只问一个**：四种模式各有一套固定问题，逐字照 `references/question-banks.md` 问，优先给选择题，前后合计最多八问；用户的说法落进模糊受众、功能堆砌这类模式时，按同一文件里的反驳表回应。
- **方案至少两个，推荐引用用户原话**：每个方案写清做什么、不做什么、优点、缺点和适合场景，依赖的假设全部列出；推荐点明依据的是用户哪句话，写成「因为用户说了 X，所以推荐 Y」（`SKILL.md` 方案生成与质量规则两节）。
- **交给用户前先过一位怀疑论者**：思考文档写完，派一个独立的子 agent 找最容易失败的点、最大的盲区、资源减半时该砍什么，结果附在文末，再请用户确认（`references/thinking-doc-template.md`）。
- **决策逐轮追加，换个会话也接得上**：产品模式的思考文档用「追问 → 选项 → AI 倾向 → 答：」记每条决策，新一轮审视另起一节，「答：」只由用户填；文档开头固定一节「如何继续这次讨论」，写明从哪读起、下次第一句说什么，格式在 `references/thinking-doc-template.md`。

```text
forge-brainstorm/
├── SKILL.md                       铁律、四种模式、各阶段做法
└── references/
    ├── question-banks.md          四种模式的提问原文和反驳话术
    └── thinking-doc-template.md   思考文档结构、对抗审查、续聊指引
```

## 其他

- 前提：景观感知要用 WebSearch；画图辅助用 Mermaid 或生图工具，没有生图工具时只保存 prompt，不假装已经生成
- 注意：思考文档是原始讨论，默认归档；用户确认后的结论才写进项目的当前文档
