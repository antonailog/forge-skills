# forge-dev

开发调度：子 Skill 各开上下文

## 要解决的问题

从 PRD 到交付要依次跑设计、工程、QA。全放在一个会话里顺序做，调度和执行抢同一个上下文，越往后输出越差：搭这套流程时，同一个会话做到第三个 Skill，方案就明显粗糙了。子任务做完说一句「完成了」，也不等于真的完成。

## 运行方式

![forge-dev 结构图](../../docs/diagrams/forge-dev.jpg)

先查有没有 PRD 和 Feature Spec：缺了就建议回 forge-prd，用户也可以选轻量模式直接跳到执行计划。默认的交互模式在三处停下等确认，--auto 只在开头对齐一两轮，之后不再停。每个子 skill 开一个新 Agent，主上下文只传文档路径，回来后读它的产出文档核对，再进下一个 Wave。

## 关键设计

- **主上下文只编排，不干具体活**：每个子 skill 拿一个全新的上下文；代价是对话里的信息传不过去，所以偏好和调研先写成 CONTEXT.md、RESEARCH.md，靠文件交接
- **不信子 agent 的口头汇报**：回来后看 `git diff --stat`，读 DESIGN.md、ENGINEERING.md、QA.md，确认确实写了
- **动手前先收偏好**：PRD 说了做什么，怎么做还有灰区（布局偏好、返回格式、命名、目录结构），逐个给推荐让用户选
- **按任务性质选模型**：跑测试、批量重命名、填模板用便宜模型；架构、设计、审查不降级
- **全自动也不替人提交**：--auto 不 git commit，改动留在工作区，每个阶段存一份 patch；遇到阻塞跳到能做的阶段，在报告里标出来

## 其他

- 不处理：设计、写代码、测试本身，分别由 forge-design、forge-eng、forge-qa 在子 Agent 里做；这三个也能单独调用，不经过调度器
- 前提：宿主要能开子 Agent
- 注意：一条流水线只做一个想法，不塞多个不相关的功能
