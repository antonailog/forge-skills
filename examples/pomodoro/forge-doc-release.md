# forge-doc-release

## 输入

- 合并请求 #1 已经合进 main（见 [forge-ship.md](forge-ship.md)），番茄钟页面、计时规则、单测、工程文档、验收手册、截图都在 main 上了。
- 仓库现有文档：根目录 `README.md` 只有三段项目介绍，没写这个番茄钟能做什么、怎么打开；`CLAUDE.md` 的「项目特化规则」还是空的占位；`docs/` 下 PRD、DESIGN、ENGINEERING、需求设计文档开头的状态还停在「待设计 / 待实现 / 待验收」；没有总的版本记录，也没有 `VERSION`、待办文件。
- 并行情况：forge-bugfix 会话在自己的隔离副本里修主按钮颜色过渡，可能会改设计文档、验收手册里相关的段落。

## 用户会怎么说

「合进去了，把文档同步一下：README 写清这是什么、怎么打开用，再补个更新记录。」（或者直接 `/forge-doc-release`）

## 过程

0. **找位置跑（开工前）**：Skill 设计成「发布之后、合并之前」在功能分支上跑，在基础分支上会直接中止；可这次 forge-ship 走的是完整发布，合并请求已经合进去了，没有可用的功能分支。又因为 forge-ship 规定「进 main 必须走合并请求」，所以从最新的 main 拉了一个文档分支 `docs/release-2026-10-23`，放在单独的隔离副本里做——不碰 main 的检出（修 bug 的会话也在用它看状态），也不碰修 bug 的分支。
1. **定基础分支、看这次发布带来了什么（第 0、1 步）**：基础分支 main。文档分支本身相对 main 没有改动，按 Skill 的比较方式什么都看不到，于是改为比较合并请求 #1 带进来的全部内容。分成四类：新功能（番茄钟页面本身）、行为变更（审查修的那一处）、没有移除、基础设施（单测、验收脚本、截图脚本）。找到要审的文档十几份。
2. **逐份审（第 2 步）**：
   - 根目录 `README.md`：没写能做什么、怎么打开、怎么验证——要加整节新内容，按 Skill 归为「要问」。
   - `CLAUDE.md`：没写任何命令；forge-ship 跑测试时要找「项目文档里记录的测试命令」，这里是空的——加新内容，归为「要问」。
   - PRD、DESIGN、ENGINEERING、需求设计文档：开头状态过时——事实性更正，归为「直接改」。
   - 版本记录：仓库里没有。按文档规范，总的版本记录放在 `docs/CHANGELOG.md`（Skill 和 forge-ship 找的都是根目录的 `CHANGELOG.md`）——新建文件，归为「要问」。
   - 验收手册：记录的是验收那一刻测了哪个提交，属实，不改；设计文档里「悬停 120ms 过渡」和「切换时直接换色」的矛盾归修 bug 会话，不碰。
   - 两份本轮开发调度产物写着「迭代结项后归档」：修 bug 和复盘还没做完，这轮还没结项，不动。
3. **直接改（第 3 步）**：
   - `docs/PRD.md`：状态「需求已确认，待设计」→「已实现，v1.0 已合进主分支（未部署）」，附合并请求链接。
   - `docs/DESIGN.md`：状态「已确认（待实现）」→「已实现」。
   - `docs/ENGINEERING.md`：状态「待验收」→「已通过验收、已合进主分支」；迭代摘要补一条「上线前审查修正」。
   - `docs/modules/番茄钟.md`：阶段「已实现，待验收（代码在功能分支上）」→「已发布——验收通过，已合进主分支（还没有部署到网上）」。
4. **要问的三处（第 4 步）**：
   - 演示时由 AI 按默认确认：A「README 补四节」——能做什么、怎么打开（双击 `index.html`，或起一个本地静态服务）、怎么验证、文件和文档；原来的项目介绍一字不改；配一张真实页面的状态总览图。
   - 演示时由 AI 按默认确认：A「新建 `docs/CHANGELOG.md`」——写 v1.0 一条，分「你现在可以」「已知限制」「贡献者相关」，开头用户能做什么，不写实现细节。
   - 演示时由 AI 按默认确认：A「`CLAUDE.md` 补项目特化规则」——纯静态、不加依赖、不请求外部网址；样式和行为只通过 `style.css` 文件头的接口对接；验证命令。文档位置加一行版本记录。
5. **润色版本记录（第 5 步）**：Skill 只润色已有条目、分支没改版本记录就跳过；这次是新建的，按「推销测试」写成了「你现在可以……」开头，没有别的可润色。
6. **跨文档一致性和可达性（第 6 步）**：根目录 `README.md` 新加了文档入口链接后，所有文档都能从 `README.md` 或 `CLAUDE.md` 走到，相对链接全部有效。需求设计文档检查第一次没通过：阶段那一行写了版本号，检查脚本把版本号当成「讲历史的词」拦下（需求设计文档只写现在）；去掉版本号后通过。
7. **待办、版本号（第 7、8 步）**：没有待办文件、没有 `VERSION`，按 Skill 静默跳过；改动里也没有新的待办注释。
8. **提交、走合并请求（第 9 步）**：按文件名暂存九个文件、一个提交、推送；开合并请求 #2，描述里按 Skill 要求有「## 文档」一节，逐个文件写改了什么。然后照 forge-ship 的规矩做合并前检查（可合并、无远程检查、不要求审批）、保留分支历史合并、本地 main 快进同步。最后删掉这一步自己建的隔离副本和本地文档分支（干净、已合并）；功能分支的隔离副本和修 bug 的隔离副本都没碰。

文档健康摘要：

```text
文档健康:
  README.md       已更新（补「能做什么 / 怎么打开 / 怎么验证 / 文件和文档」四节，配真实页面截图）
  ARCHITECTURE.md 跳过（文件不存在）
  CONTRIBUTING.md 跳过（文件不存在）
  CHANGELOG.md    已更新（新建 docs/CHANGELOG.md，写 v1.0 一条）
  TODOS.md        跳过（文件不存在）
  VERSION         跳过（文件不存在）
  CLAUDE.md       已更新（项目特化规则三条；文档位置加版本记录）
  PRD / DESIGN / ENGINEERING / 需求设计文档  已更新（状态同步到已发布）
```

## 问题

- **跑的时机和完整发布对不上（最值得修）**：Skill 写的是「发布之后、合并之前」在功能分支上跑、在主分支上直接中止；可 forge-ship 的完整发布会一口气合并完，之后就没有功能分支了。只能另拉文档分支、再开一个合并请求、再合一次。要么 forge-ship 完整发布在合并前调它，要么 Skill 写明合并后怎么跑。
- **合并后比较方式失效**：第 1 步拿当前分支和主分支比，新拉的文档分支和主分支没有差别，什么也看不到；只能自己改成比较上一个合并请求带进来的内容。
- **版本记录放哪，三份规范说法不一**：forge-ship 和本 Skill 找根目录 `CHANGELOG.md`，文档规范把总账放在 `docs/CHANGELOG.md`；而且 forge-ship 没有版本记录就跳过、本 Skill 又说「条目由 forge-ship 写，我只润色」，结果谁都不建。这次按文档规范新建在 `docs/` 下，是代答拍板的。
- **「绝不用 Write 写版本记录」没考虑新建**：规则本意是不覆盖已有内容，可文件不存在时只能新建；Skill 没写这种情况。
- **需求设计文档的状态归谁改没说**：它归 forge-feature-doc 维护，有自己的检查；本 Skill 的「其他 .md 文件」只说「检查是否矛盾」。这次直接改了阶段那一行，还被检查脚本以「写了版本号」拦了一次。功能登记表 `.features/` 里这个功能也还是「进行中」，Skill 不管、forge-ship 也不管。
- **提交署名模板和项目规范不一样**：Skill 的提交模板写死了一个通用署名行，这次按项目规范换成了带模型名的那一行。
- **非交互只能代答**：三处「要问」本该弹选择框，示范里由 AI 代答。
- **不适合宣传的地方**：为了把文档合进 main 多开了一个合并请求，「一次发布」实际是两个合并请求；README 和版本记录的初稿是 AI 自己写、自己代答通过的，没有人审过措辞。
