# forge-feature-doc

## 输入

上一步定稿的 `docs/PRD.md` 和 `.features/pomodoro-timer/feature-spec.md`，以及需求讨论原文 `docs/archive/raw/discussions/番茄钟/2026-10-23-番茄钟-需求讨论.md`。forge-prd 的最后一步要求调用本 Skill。

## 用户会怎么说

「PRD 太长了看不过来，给我出一份能看懂的设计文档。」（或者不用说：forge-prd 收尾时自动接上。）

## 过程

1. **读资料、判类型**：读文档入口、PRD、Feature Spec 和讨论原文。判断这个功能「有界面、没有后端、没有 AI」。
2. **建骨架**：跑 Skill 自带的脚手架，生成文档骨架、示意图模板，并把出图和检查两个脚本复制进项目。
3. **填内容**：开头一句话、所处阶段、待拍板；然后背景、目标与成功标准、用户流程、页面布局、状态一览、交互与细节、业务规则；末尾「细节在哪」链接表和关键改动。
   - 按类型规则，「业务规则」一节只给有后端的功能写。但这个页面虽然没有后端，「什么算完成一个」「刷新后怎么恢复」恰恰决定完成数对不对，所以手动保留了这一节，并在节首说明原因。
   - 关键改动从讨论记录和变更日志里挑了三条影响效果的：任何时候都能跳过、刷新后接着走、标题把剩余时间放最前面。
4. **待拍板**：只放真正还没定的一条——后台标签页里铃声可能晚响，要不要加桌面通知（建议先量再定）；另把「手机锁屏不保证提醒」「同时开两个页面各走各的」合成一行「建议接受现状，你不回就按此」。
   - 演示时由 AI 按默认确认：这两处按建议接受现状；后台铃声一条留在待拍板，等验收实测后再定。
5. **出图**：还没有设计稿也没有页面，按 Skill 规定画「页面示意」（用真实文案、编号标区域、注明不是截图）。共六张：现状问题、用户流程、页面布局、六种状态、标签页标题细节、按钮细节。用 Skill 的脚本渲染成图片后逐张查看，改了两处：布局图里「已暂停」配的却是「暂停」按钮，统一成暂停态；标题细节图里交替的那个标签被截断看不到完成数，放宽。
6. **检查**：跑 Skill 的检查脚本。第一次没通过：业务规则里一句「那段在今天之前就结束了」被当成「讲历史的词」拦下，改成「今天零点前」后通过。
7. **收尾**：在文档入口和索引里加上这份文档；文档、图和图的源文件一起提交。Skill 要求最后在编辑器里打开文档，这次是无界面运行，跳过。

## 问题

- **「业务规则」被绑在「有后端」上**：类型对照表规定只有有后端的功能才写业务规则，脚手架按「只有界面」生成时直接删掉了这一节。纯前端页面也会有决定对错的规则（这次的计数口径和恢复规则），只能手动加回来。
- **还没开发时「⏳」没法用**：Skill 说只标例外、不标的默认「已定且已做完」。需求阶段所有内容都是「已定未做」，逐条标满篇都是，不标又会被误读成已上线。这次只能在「阶段」一行里统一说明。
- **还没有代码时盯什么**：检查脚本靠文档开头列的「盯住的文件」判断文档是否落后，但需求阶段还没有代码。留空的话检查会直接跳过这份文档（等于没检查）；写一个还不存在的文件又会报错。这次改为盯 PRD 和 Feature Spec，Skill 没给这种情况的说法，后面写代码时还得记得把页面文件加进来。
- **和文档治理规范的开头信息不一致**：本 Skill 模板的开头身份信息用 `status: current`、`updated`，没有 `type`；forge-doc-policy 规定状态只能是 live / draft / archive，且必须有 `type` 和 `last_updated`。两个 Skill 对同一份文档的要求打架。
- **「讲历史的词」误伤**：检查按字面拦「之前」「不再」这类词，描述现行规则的「今天之前」也被拦，只能换说法绕开。
- **阶段说法前后不一**：阶段对照表说 PRD 阶段只需出现状图和流程图，新建流程却要求有界面就出页面图。这次按新建流程画了页面示意。
- **背景图的依据偏弱**：「现在的问题」要用失败的例子，但新产品的失败例子只能来自需求方对现有工具的抱怨；这次的抱怨在头脑风暴里是 AI 按设定反推的。图上注明了来源，宣传时不要把这张图说成实测数据。
- **往项目里塞了脚本**：脚手架会把出图和检查脚本复制进项目的 `scripts/` 目录。这一棒本来只产出文档，仓库里却多了几份脚本文件，宣传时需要说明它们是文档工具，不是业务代码。
