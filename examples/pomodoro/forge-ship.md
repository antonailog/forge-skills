# forge-ship

## 输入

- 功能分支 `eng/pomodoro-timer-2026-10-23`（隔离副本 `.worktrees/pomodoro-timer`）：第 3 棒的设计实现、工程、验收提交，加上 forge-review 刚修好、还没提交的五个文件（见 [forge-review.md](forge-review.md)）。
- 主分支 main：在功能分支拉出来之后，第 3 棒又往上补过一次功能状态更新。
- 并行情况：开工时发现 forge-bugfix 会话已经从功能分支拉出了 `bugfix/bf-1023-1` 和它自己的隔离副本，本棒只读看了一眼，不碰。

## 用户会怎么说

「审完了，发布吧：开合并请求、合进 main，本地 main 也同步一下。」（或者直接 `/forge-ship`）

## 过程

1. **前置检查、定模式（第 0 步）**：当前在功能分支，不是 main；还没有合并请求；仓库默认分支是 main。用户说了「合进 main、本地也同步」，按 Skill 走 Full ship（完整发布）。
2. **列出仓库外的写操作（第 0.5 步）**：本轮只有三件——推送功能分支、创建合并请求、合并合并请求，都在示范仓库里；不部署、不改数据库、不动任何第三方账号。
   - 演示时由 AI 按默认确认：这三件按示范规矩已获授权，一次批准，不逐个问。
3. **安全检查（第 1 步）**：工作区里是 forge-review 留下的五个改动文件，没有缓存或构建产物；顺手找到本地 main 所在的位置（项目根目录），干净，先不动。
   - 演示时由 AI 按默认确认：A「把本次相关改动加入并提交」——只加审查改的五个文件，单独一个提交，提交信息写清由 forge-review 发现。
4. **把 main 合进功能分支（第 2 步）**：main 上那次状态更新合进来，没有冲突。自动生成的合并说明是英文，改成中文并补上署名行（还没推送，可以改）。
5. **跑验证（第 3 步）**：项目文档里写的单测命令全部通过；需求设计文档检查通过。浏览器回归在审查那一步刚用假时钟跑过、之后只多了 main 上的状态文件，没有再跑。
6. **发布前再看一遍改动（第 4 步）**：没有调试代码、密钥、个人路径、构建产物；打印输出只出现在截图和验收脚本里（那是给终端看的进度），页面代码里没有。仓库是公开的，这一项特意查了。
7. **变更日志、版本号（第 5 步）**：仓库没有 `CHANGELOG.md` 也没有 `VERSION` 文件，按 Skill 跳过，留给下一步 forge-doc-release。
8. **推送、开合并请求（第 6–8 步）**：推送功能分支；创建合并请求，描述按 Skill 要求写了变更摘要、测试情况、注意事项、要不要部署、有没有数据或 prompt 变更，末尾加了 Claude Code 署名行。注意事项里写明两件事：页面在后台时到点会晚响、需要人工验证；主按钮颜色那处小偏离由另一个修 bug 的会话单独处理。
9. **合并前检查（第 9 步）**：合并请求是打开状态、不是草稿、没有冲突、不要求审批；**仓库没有配置任何远程自动检查**，所以总结里只能写「无远程检查」，不能写「CI 已通过」。
10. **合并（第 10 步）**：按 Skill 推荐用保留分支历史的合并方式，不删远程分支；合并说明改成中文、带署名。合并后远程 main 指向这次的合并提交。
11. **同步本地 main（第 11 步）**：本地 main 干净、只落后不分叉，直接快进到远程 main；两边指向同一个提交后才写「已同步」。在 main 上又跑了一遍单测，通过。
12. **隔离副本怎么处理**：Skill 没有「合并后清理隔离副本」这一步，远程分支也按 Skill 默认保留。所以 `.worktrees/pomodoro-timer` 原样留着——里面没有未提交的东西，只有被忽略的 Codex 任务书、工程验收脚本和 QA 运行文件。清理归 forge-status（只在用户明确要求时删）。
13. **发布总结（第 12 步）**：

```text
+====================================================+
|                  Ship Summary                      |
+====================================================+
| 模式：Full ship                                     |
| 功能分支：eng/pomodoro-timer-2026-10-23             |
| 基础分支：main                                      |
| 提交：67653df（审查修正）、ca8453e（合入 main）      |
| PR：https://github.com/antonailog/forge-demo-pomodoro/pull/1 |
| PR 状态：已合并                                     |
| 远程基础分支：2282272                               |
| 本地基础分支 worktree：项目根目录                    |
| 本地基础分支状态：已同步                             |
| 测试：通过（本机；无远程检查）                        |
| CHANGELOG：未更新（仓库还没有，交 forge-doc-release） |
| 部署：未执行                                        |
+====================================================+
```

线上部署未执行。本次 ship 只表示代码进入远程 main，并同步了本地 main。

## 问题

- **合并后谁清理隔离副本、谁标「已发布」都没写（最值得修）**：Skill 合并完就结束，没有处理隔离副本这一步，也不更新功能登记表——`.features/` 里这个功能还是「进行中、由 forge-dev 负责」，隔离副本和本地分支都留着，要等 forge-status 巡检才会被当成「已合并、可清理」。
- **发布前看改动用的也是「直接比」**：和 forge-review 一样，第 1、4 步拿分支和 main 现在的样子直接比；这次因为第 2 步先把 main 合了进来，第 4 步才没被误导，但第 1 步看到的清单仍然混着 main 的改动。
- **「要不要提交」问了两遍**：forge-review 说自己绝不提交，forge-ship 第 1 步看到未提交改动又问一次，第 6 步「最终提交」和第 1 步的提交是什么关系也没写清楚。
- **自动生成的合并说明是英文、没有署名**：把 main 合进功能分支、合并合并请求这两处都会自动生成英文说明，Skill 没提醒按项目的提交信息规范改写。
- **「生产写面授权门」按带服务器的项目写**：示例全是部署、数据库、改服务器配置；纯静态页面只有「合并自己的合并请求」一项，照模板列清单显得很重。
- **没有远程检查时缺一句提醒**：Skill 只规定不能说「CI 已通过」，没建议在合并请求描述里写明「本仓库没有远程检查，以上是本机结果」——这次是自己加的。
- **不适合宣传的地方**：这次没有部署，「上线」只是合进 main；宣传时要说「合并发布」，别说「上线到网上」。合并请求是 AI 自己开、自己合的，没有第二个人审批。
