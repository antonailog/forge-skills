# forge-qa

## 输入

- forge-dev 调度进来，Mode A 完整验收。被测代码在隔离副本 `.worktrees/pomodoro-timer`（分支 `eng/pomodoro-timer-2026-10-23`），调度器已在副本根目录起好本地静态服务，验收只认这一个地址。
- 验收依据：`.features/pomodoro-timer/feature-spec.md` 第五节验收检查表和各需求的异常态表；`docs/DESIGN.md`（颜色、字号、间距的具体值）；`docs/ENGINEERING.md` 第七节测试矩阵（单元、页面、人工三层）；`docs/PRD.md`；`docs/v1.0-RESEARCH.md` 坑点表。
- 设计页面包 `docs/assets/visuals/pomodoro/`（骨架、决策文件里配好的「骨架与真页面自动比对」清单）；两张气质稿只作观感参考。
- forge-eng 的交接：页面里没有测试钩子，造时间靠浏览器的「假时钟」；它点名留给 QA 的几件事——页面在后台时到点晚响多少、电脑睡眠唤醒、手机锁屏、声音能不能听见、Safari 和 Firefox；还有一处已知的样式偏离（到点切阶段时主按钮颜色有一下极短的过渡，设计写的是直接切换）。

## 用户会怎么说

「功能做完了，帮我验收一下：按需求里的检查表一条条测，到点提醒在后台到底准不准也测一下，有问题列出来，别动代码。」

## 过程

0. **上下文探测（第 0 步）**：确认在功能分支的隔离副本里测；找到 PRD、Feature Spec、DESIGN、ENGINEERING、调研和视觉决策索引；本次改动就是整个页面，按全量测、同时盯住几个新文件。扫了一遍页面里能用的定位方式：项目没有专门的测试标记，就用设计实现留下的业务锚点和语义标签，不编造。还摸了一遍测试环境：本机的 Safari 内核、Firefox 内核和测试工具版本对不上（Safari 内核启动后通信协议不兼容，Firefox 没装），按规矩不为测试改环境，这两项转为需求方手动验证。
   - 演示时由 AI 按默认确认：测试级别选「详尽」（调度器要的是完整验收、检查表每一项都要有结论，DESIGN 里也有键盘和读屏的要求）。
1. **健康基准（第 1 步）**：先打开页面看一眼——空状态正确、控制台零错误、只加载了自己的几个文件。项目原有的规则单测也重跑一遍，全过。
2. **生成测试规格（第 2.5 步）**：把检查表的每一条、DESIGN 的每个具体数值、工程补齐的三条口径、调研坑点，都写成可判对错的用例，每条都标明出处，并自检「每条至少有一个验证内容而不是只验证元素存在的断言」。十个测试维度里，实时推送、网址状态、异步加载三项这个纯静态页面用不上，写明原因后跳过。
3. **验收计划（第 3 步）**：整理成人能看懂的计划——先看整体流程和页面结构，再逐项看功能、视觉数值、可访问性，最后列出只能在真实环境验的几项。
   - 演示时由 AI 按默认确认：按计划执行，不增减测试项。
4. **执行（第 5 步）**，分四个阶段：
   - **冒烟**：全程盯控制台和网络请求，零错误、零外部请求；本地双击打开和用网址打开行为一致。
   - **核心功能**：用「假时钟」把 25 分钟快进完，逐条验开始、暂停、跳过、到点、刷新恢复、关着页面时到点、跨过零点、把系统时间往回调、同时开两个页面、浏览器不让保存或中途存满、没点过按钮时声音被拦截、到点后点一下或按个键停止标题交替；把十几种损坏或过期的本机记录逐一塞进去，看页面是否都当作没有记录、不报错。
   - **视觉与响应式**：读浏览器算出来的样式，和 DESIGN 的颜色、字号、间距、圆角、焦点框逐项对照，全部一致；用设计工作台的比对脚本把骨架和真页面放在同一尺寸下比，五个锚点完全重合，两张截图一模一样；常见手机竖屏、很窄的小屏、手机横屏、平板、笔记本、桌面都不重叠、不截断。零件库守门这一项，项目没有零件库，按 Skill 跳过并记下「不算通过」。
   - **可访问性**：用本机已有的检查库（不从外网加载，守住 PRD「不请求外部网址」）扫了四种状态，没有违规；键盘能依次走到两个按钮，回车、空格能开始和暂停，焦点框只在键盘操作时出现。
   - **真实时间**：不快进，真的点「开始」等满 25 分钟专注、再等 5 分钟休息，量提示音实际响的时刻。
5. **后台到点怎么测的（任务交接的重点）**：
   - 先想让无头浏览器里的标签页转入后台：试了最小化窗口、同一窗口开新标签并切过去，页面始终认为自己「在眼前」，浏览器也就不会放慢它。**真实的后台场景这一步测不了**。
   - 能量到的是「页面在眼前」的情况：真实等满 25 分钟，提示音几乎准时，只响一次，标题交替、点一下后停止都对。
   - 再按浏览器对长时间隐藏页面的限速方式做了个模型：让页面每分钟只「醒」一次。结果是提示音在结束后第一次醒来时响起，晚了不到一分钟，不会重复响、也不会重复计数。这是模型推断，不是实测。
   - 电脑睡眠用「把页面所在的进程整个挂起、真实时间照走、再恢复」来近似：恢复的一瞬间就完成到点处理并响铃。
   - 需求方要在真实浏览器里手动验：点开始后切到别的软件，到点时看表记录晚了多久；另外合盖睡眠、手机锁屏、试听音量、Safari 和 Firefox 各走一遍，步骤写在验收手册里。
6. **QA 自己的工具也出过错**：第一版「冻结页面」用的是浏览器调试接口里的一个冻结命令，命令说成功了，页面却照常走秒，量出来的结果作废（留档标明作废），改成挂起进程，并加了自检——挂起期间页面一次都不能动。验收脚本里还有两处自己写错的地方（时间算错没跨过零点、一个函数调用写法丢了上下文）和一处测法不对（对已经被键盘选中的按钮再点鼠标，浏览器本来就会保留焦点框）。都是先查清是工具问题、修工具后重跑，没有记成页面的 bug。
7. **智能分析（第 6 步）**：最后一轮干净跑下来，只剩一项不过——到点或点跳过切阶段时，主按钮颜色不是直接换，而是在极短时间里经过一串中间色；查到根源是样式里给「鼠标悬停」用的颜色过渡，阶段换色时也被带上了，是设计实现那一步引入的。按 Skill 的严重度表定为「低」（外观细节、不影响功能），归类为「设计取舍、待用户判断」，不自动转去修 bug；修复清单写明先由 forge-design 拍板，要改样式再交给 forge-design-impl。另记了几条不算 bug 的观察（工程文档里补齐口径的条数写少了一条、极小的手机横屏需要上下滚动、需求里「显示的剩余时间不多于真实剩余」和「向上取整到秒」措辞有张力）。
8. **写 QA 文档、提交（第 4、8 步）**：新建验收手册 `docs/QA.md`（先全局后细节：整体流程和结构结论 → 检查表逐项结论和证据 → 设计数值实测表 → 问题与修复清单 → 后台到点的测法和结果 → 验收命令与回归清单）；挑出关键截图放进 `docs/qa-screenshots/`，验收脚本和测试规格放进 `scripts/qa/`，文档入口和索引各补一行，在功能分支上单独提交；业务代码一行没动。功能状态文件里 QA 一行和各验收项的状态由调度器统一提交。
9. **用户验收关卡（第 7 步）**：检查表里功能、视觉、流程各项都通过，只有「后台真实到点」是部分验证；唯一不过的是那处颜色过渡，它在需求设计文档的「待拍板」里早就列过，默认「接受现状」，按「简洁、安静、不要花哨动效」的需求设定也可以接受。
   - 演示时由 AI 按默认确认：颜色过渡按需求设计文档待拍板的默认「接受现状」处理，不阻塞发布，交 forge-design 拍板是否改设计文档。
   - 演示时由 AI 按默认确认：验收通过（accept），下一步 forge-review、forge-ship；后台到点、睡眠、真机、试听、Safari 和 Firefox 由需求方按清单手动验。

## 问题

- **最难的一项测不了，Skill 也没给办法**：Feature Spec 要求「页面在后台时到点会响、记录晚了多久」，但无头浏览器里标签页永远「在眼前」，浏览器不会放慢它。Skill 的十个维度都围绕带接口的网页应用（接口、实时推送、网址状态、懒加载），没有「真实时间 / 后台 / 睡眠」这一类，也没说测不了时怎么降级、怎么交接给人；这次是自己设计了真实等待、进程挂起和每分钟唤醒模型，并把手动步骤写进手册。
- **Skill 自带的测试框架在本机直接加载不了**：它要求「必须用 qa-runner」，但这个文件用新式模块语法引用测试工具，全局安装的工具找不到，要先复制到能找到依赖的目录才能用；它也没有时钟、注入脚本、多页面等选项，大部分用例还是得自己建浏览器环境。
- **报告放哪和文档规范打架**：Skill 把报告、测试规格、截图都写到被 git 忽略的目录里，回归要用的东西下次换个副本就没了；文档规范又说 `docs/QA.md` 只写「方法、命令、用例、证据」。这次的取舍是：结论和方法写进 `docs/QA.md`，脚本和规格进 `scripts/qa/`，挑过的截图进 `docs/qa-screenshots/`，完整输出留在忽略目录，报告因此存了两份。Skill 还说「改了长期验收规则就写进总变更日志」，项目没有这个文件，没新建。
- **两套健康评分公式**：执行手册和报告模板各给了一套维度和权重不同的算法，没说用哪套（这次用执行手册那套）。
- **「有失败就打回」和上游的待拍板打架**：唯一不过的颜色过渡，DESIGN 说「直接切换」，需求设计文档的待拍板却默认「接受现状」，工程那一步也已经代答接受。Skill 的验收关卡只有「通过 / 不通过 / 我先体验」，上线标准只讲严重、高、中，没讲「低级别、且需求方已默认接受」的失败该怎么判；这次靠调度器给的「只剩可接受的已知边界就通过」才落地。三个 Skill（设计实现引入、工程记下、QA 判失败）对同一处偏离各说各的，谁来改设计文档没人负责。
- **测试模板和本项目大量不符**：可访问性模板从外网加载检查库，和 PRD「不请求外部网址」冲突（这次改用本机已有的一份）；视觉模板里的固定间距网格检查、社交平台配色、卡片详情面板都用不上；前置脚本在没传入地址时会去试几个常见端口，和它自己「不得猜端口」的铁律矛盾（这次调用方传了地址，没走到这一步）；「每步截图并展示给用户」在几十个状态下不现实。
- **跨浏览器没有对应维度**：Skill 不提 Safari 和 Firefox，本机内核版本又对不上，只能交给需求方手动验。
- **非交互运行只能代答**：测试级别、验收计划、用户验收关卡三处都要停下来问人，演示里全部由 AI 代答。
- **不适合宣传的地方**：
  - 用户最关心的「后台到点晚多久」没有真正测到，只有前台实测和一个模型推断；宣传时不能说「已验证后台准时提醒」。
  - 提示音只证明「发出了一声」，没有人真的听过。
  - QA 自己的工具和脚本错了好几次（冻结命令其实没生效、时间算错、函数写法、测法不对），都是在把失败记成 bug 之前先排查出来的——适合讲「先怀疑工具」，不适合讲「AI 一次写对了验收脚本」。
  - 唯一抓到的问题是一处几乎看不见的颜色过渡，「QA 抓出大 bug」的故事不成立；更适合讲「每一项都有结论和证据，连设计数值都逐个核对到位」。
