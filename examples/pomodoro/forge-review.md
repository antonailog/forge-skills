# forge-review

## 输入

- 功能分支 `eng/pomodoro-timer-2026-10-23`（隔离副本 `.worktrees/pomodoro-timer`），第 3 棒交付、QA 已通过、还没合并。审查对象是它相对 main 的全部改动：页面结构与样式、计时规则 `timer-core.js` 和单测、页面接线 `app.js`、工程文档、验收手册与脚本、截图。
- 判断口径用的文档：项目 `CLAUDE.md`、`docs/README.md`、`docs/INDEX.md`、`docs/ENGINEERING.md`（规则口径表、第九节「交给审查决定」的技术债）、`.features/pomodoro-timer/feature-spec.md`。
- 并行约定：「切换阶段时主按钮颜色有极短过渡」归同时在跑的 forge-bugfix 会话修，本棒不碰相关样式。

## 用户会怎么说

「QA 过了，上线前帮我审一遍代码，有问题直接修。」（或者直接 `/forge-review`）

## 过程

1. **定基础分支（第 0 步）**：功能分支还没有合并请求，读仓库默认分支得到 main。
2. **看分支改了什么（第 1、2 步）**：按 Skill 的命令拿到相对 main 的改动清单，发现里面混进了两份功能状态文件、而且是「删掉了一大段」——其实那是第 3 棒在拉分支之后往 main 上补的状态更新，Skill 的比较方式把「main 后来多出来的」算成了「分支删掉的」。改用「只看分支自己改了什么」的比较方式，两份状态文件就不在了，再从头读完全部代码改动。
3. **两轮审查（第 3 步）**：
   - 第一轮四类严重问题里，数据库、AI 输出两类这个纯静态页面没有；「两个页面同时改记录」看了读取、合并、写回的顺序，同一段只算一次、完成数取大者，工程文档也写明两个页面的计时不同步，不算问题；阶段和状态的取值在规则、页面、样式三处一致。
   - 第二轮找到三处值得改的地方，详见下一步。网页转义没问题（页面只写纯文字）；项目没有零件库，「设计值越界」一项按 Skill 跳过。
4. **修复（第 4 步）**，摘要：「上线前审查：4 个问题（0 严重，4 信息性）」。
   - **[已自动修复]** `app.js`：走秒间隔和提示音的几个参数是裸数字，提成带注释的常量，数值不变。
   - **[需要确认 1]** `timer-core.js` 暂停那一行：系统时间被往回调之后点暂停，存下的剩余时间比一整段还长——页面显示 25:00，点「继续」后数字却停着不动，要多等一阵才开始走；刷新一次又变回真正的 25:00，同一个状态刷新前后表现不一样。工程文档写的口径是「剩余时间一律不超过本段时长」，显示和恢复记录都照做了，只有暂停这一处漏了。更值得说的是：原来的单测把这个错误行为写成了「应当如此」。修法：暂停时也用同一个取值函数；先改单测、确认它在旧代码上失败，再改实现。
     - 演示时由 AI 按默认确认：A「按建议修复」（需求设定「没说到的选最不打扰用户的」，点继续就该马上走）。
   - **[需要确认 2]** `app.js`：页面读取元素、刷新文字、绑定按钮也都包在空的错误捕获里。这是工程那一步留下、写明「交给审查决定」的技术债。审查判断它不只是多余：页面锚点一旦被改坏，按钮会静默失灵、控制台一个错误都没有，QA「控制台零错误」的检查就形同虚设。修法：只在存储和声音两处保留错误捕获（浏览器设置确实可能让它们失败），其余去掉；工程文档第九节删掉这条技术债，第三节补一句口径，工程变更日志加「上线前审查修正」一节。
     - 演示时由 AI 按默认确认：A「按建议修复」。
   - **[信息性，不在本步改]** 根目录 `README.md` 没写这是什么、怎么打开用；`docs/ENGINEERING.md` 开头状态还写着「待验收」。按 Skill 标为「文档可能过时」，交给发布后的 forge-doc-release。
   - **[已知，不归本棒]** 主按钮颜色过渡：forge-bugfix 会话在修，本棒没有动 `style.css`。
5. **待办交叉检查（第 5 步）**：仓库根目录没有待办文件；Bug 任务池 `docs/bugfix/backlog.md` 里只有模板示例，本次没有解决或新增条目。
6. **文档过时检查（第 6 步）**：需求设计文档检查脚本通过。
7. **验证**（Skill 没要求，按项目 `CLAUDE.md`「提交前自验」补做，全部用快进的假时钟，不按真实时间等）：
   - 单测全部通过。
   - 浏览器回归：从 QA 留下的验收脚本里挑出和这次改动有关的几组（开始暂停跳过、时间回调、到点、提示音被拦、刷新恢复、两个页面、损坏记录、不能保存、键盘操作），全部通过，控制台零错误。为了不覆盖 QA 留下的运行结果，输出写到了临时目录，并单独起了一个本地服务，跑完关掉。
   - 针对修掉的那处问题写了一个小检查，在修复前后各跑一次：修复前，往回调时间后暂停再继续，过两秒数字还停在 25:00；修复后，同样操作两秒后是 24:58。
8. **不提交**：Skill 规定审查「绝不提交、推送或创建合并请求」，五个改动的文件留在功能分支的工作区里，由下一步 forge-ship 提交。

## 问题

- **比较方式会把 main 后来的改动算成分支删掉的（最值得修）**：Skill 用的是「拿分支和 main 现在的样子直接比」。第 3 棒在拉分支之后往 main 补过一次状态更新，于是改动清单里多出两份「被删了一大段」的状态文件，照字面审会误报「分支回退了功能状态」。应该改成「只看分支从分叉点以来改了什么」。forge-ship 第 4 步用的是同一种比较，也有这个问题。
- **检查清单偏后端**：十类里数据库、并发锁、AI 输出、零件库四类对纯静态页面完全用不上；这次真正找到的两处问题，一处来自「测试断言的是错误行为」，一处来自「错误被静默吞掉」，清单里都没有直接对应的条目——「测试缺口」只问「有没有测试」，不问「测试断言的对不对」。
- **「修复优先」但不要求修完再验证**：Skill 没有一步写「改完重跑测试」，也没说浏览器回归怎么跑；这次是按项目 `CLAUDE.md` 的「提交前自验」自己补的。
- **「绝不提交」和交接没写清**：Skill 只说提交是 forge-ship 的事，没说修好的改动以什么状态交给它；forge-ship 第 1 步看到未提交改动会再问一次「要不要提交」。
- **待办检查只认根目录的待办文件**：Forge 自己的 Bug 任务池在 `docs/bugfix/backlog.md`，Skill 不看。
- **非交互只能代答**：两处「需要确认」本该批量弹一次选择框，示范里由 AI 代答。
- **不适合宣传的地方**：找到的问题都是边角情况（要先把系统时间往回调才会遇到），没有「审查抓出大 bug」的故事；适合讲「QA 全过之后，审查还能从测试本身找出写错的规格」。浏览器回归虽然用了假时钟，仍要跑几分钟。
