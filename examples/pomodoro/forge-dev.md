# forge-dev

## 输入

第 2 棒结束时的项目仓库（主分支，工作区干净）：

- 产品当前事实 `docs/PRD.md`，行为契约 `.features/pomodoro-timer/feature-spec.md`（六块需求的场景、异常态、验收检查表）。
- 设计真相源 `docs/DESIGN.md`、工作台导出的 `pomodoro.tokens.css`、工作台骨架和决策文件 `docs/assets/visuals/pomodoro/`。
- 功能状态 `.features/pomodoro-timer/status.md`：需求、设计两个阶段已完成，工程、验收待处理。
- 还没有任何页面代码、工程文档和验收手册。

## 用户会怎么说

「设计定了，开始开发吧。」（或者直接 `/forge-dev`）

## 过程

forge-dev 自己不写代码，只做调度：读文档、收拢灰区、做调研、定执行计划，然后把设计实现、工程、验收三个子 Skill 分别派给**独立上下文的子代理**去跑，每一步跑完读它的产出核对，再派下一步。这次运行环境允许再派子代理，三个子 Skill 都按 forge-dev 的原设计在独立上下文里执行，没有走「由调度者直接调用」的备用方案。

1. **前置检测**：跑 Skill 的检测脚本——当前在主分支、浏览器自动化工具可用、发现功能登记表、没有未完成的流水线。登记表里这个功能的最后心跳很新，不是「无人认领」。
2. **第 -1、0 步：读文档、查 Feature Spec**：有 PRD，直接进入；找到 Feature Spec，提取六块需求的场景和验收检查表，作为后面工程和验收的行为契约。判定项目类型为「纯前端」。
3. **第 1 步：收拢灰区（Discussion）**：Skill 的灰区表按「视觉功能」列了布局、密度、交互、空状态、动效五项，这五项设计阶段都已定稿，不再重开。真正没定的是工程上的四件事：提示音从哪来、文件怎么分、怎么测、本地怎么预览。写成 `docs/v1.0-CONTEXT.md`。
   - 演示时由 AI 按默认确认：视觉灰区沿用 DESIGN.md；工程灰区全部采用推荐——提示音现场合成不放音频文件、计时规则和页面接线分成两个脚本（用普通脚本引入，保证本地双击能打开）、用 Node 自带的测试工具不装依赖、用系统自带的 Python 起预览服务。
4. **第 2 步：技术调研（Research）**：写成 `docs/v1.0-RESEARCH.md`，五节：技术方案、架构（「纯规则」和「页面接线」两层、样式和行为只通过属性对接）、坑点（后台标签页计时被放慢、网页出声要先有用户操作、本机存储可能整个不可用、跨零点、系统时间回调、按键别做成快捷键、手机横屏放不下）、可复用资产（工作台已配好的「骨架与真页面自动比对」）、综合建议。
5. **第 3 步：执行计划**：设计文档已经是最新，按「不重复工作」跳过 forge-design；计划为「设计实现 → 工程 → 验收」三步依次执行。为后面三步准备了视觉决策索引（哪些图只看气质、哪个骨架用来比对）。
   - 演示时由 AI 按默认确认：选 A「按建议顺序执行全部」。
6. **开工前的两件准备**：
   - 两份调度产物和文档入口、索引的改动，先在主分支提交并推送，再从主分支拉功能分支——这样功能分支上也有这两份文件，以后合并时不会和主分支在同一张表格上打架。
   - 把隔离副本目录和 forge 的运行状态目录加进 git 忽略（forge-eng 和 codex-delegate 都要求它们不进仓库）。
7. **第 4 步：分三波派子代理**，每波一个：
   - **第一波 forge-design-impl**：在隔离副本 `.worktrees/pomodoro-timer`、分支 `eng/pomodoro-timer-2026-10-23` 上搭出整页结构和全部样式，并在样式文件开头写好给工程的「接口」（行为代码只许改哪两个属性、哪几处文字）。详见 [forge-design-impl.md](forge-design-impl.md)。
   - **第二波 forge-eng**：复用同一个隔离副本，写工程文档、计时规则和单测、页面接线、到点提醒，并把需求设计文档的图换成真实页面截图。详见 [forge-eng.md](forge-eng.md)。
   - **第三波 forge-qa**：调度器在隔离副本里起好本地预览服务、把地址交给它，按 Feature Spec 检查表逐项验收。详见 [forge-qa.md](forge-qa.md)。
   - 前两波写代码时都按规矩调用 codex-delegate，把代码派给本机 Codex 写、Claude 验收后提交，详见 [codex-delegate.md](codex-delegate.md)。
   - 每个子代理交回后，调度器不轻信它的汇报：亲自看分支上的提交和改动范围、读产出的文档和记录、自己重跑一遍单元测试、打开截图看页面，核对无误才派下一波。
   - 每波的门禁由子代理按需求方设定代答，调度器在派活时预先定了几处：工程用完整模式、测试用 Node 自带工具、分支收尾选「保留分支」、验收关卡「全部通过或只剩可接受的已知边界就接受，有失败就打回给调度器」。
8. **验收结果与阻塞处理**：验收通过，只剩一处低级别的设计偏离（到点切换阶段时主按钮颜色有一下极短的过渡，设计写的是直接切换）。它早已列在需求设计文档的「待拍板」里、默认接受现状，不阻塞发布，没有触发「打回工程修复」的回路。
   - 演示时由 AI 按默认确认：这处偏离接受现状、交 forge-design 拍板，不在本轮修。
   - 验收过程中示范统筹方要求提速、不再发起按真实时间等待的测试；这条消息到达时验收已经结束，没有影响结果。
9. **第 5 步：汇总交付**：写交付报告和面向用户的验收操作清单（每一步写清点哪里、应该看到什么）；流水线状态全部标为完成；功能状态和登记表的更新在主分支单独提交。功能分支推到远端，**没有合并进主分支、没有开合并请求**——审查、发合并请求、合并是下一棒 forge-review → forge-ship 的事。隔离副本按 forge-eng 的「保留分支」选项留在本机，本地预览服务已关闭。
   - 演示时由 AI 按默认确认：交付总结确认，下一步选 A「/forge-review」。

## 问题

- **调度表里没有设计实现这一步**（最值得修）：forge-dev 的判断表只有「设计 → 工程 → 验收」，forge-design-impl 只在视觉决策一节顺带提了一句；设计已经定稿、要先落样式时，Skill 没说该怎么排。更要紧的是，forge-design-impl 本身没写在哪个分支提交，隔离副本又是 forge-eng 的步骤——如果按字面让设计实现先跑，它会直接在主分支上提交代码。这次是调度器在派活时指定「按 forge-eng 的规矩先建隔离副本，工程接着用」才避开。
- **状态文件名前后不一**（已修，forge-skills #8 统一为 `.forge/dev-state.json`）：Skill 正文和文档规范写的是 `.forge/dev-state.json`，编排细则里写的是 `.forge/state.json`。
- **运行状态进不进仓库没人说**：文档规范把 `.forge/` 下的流水线状态、视觉决策索引列为「工作区文件」，codex-delegate 说 `.forge/` 不进 git，脚手架生成的忽略规则却只忽略了其中一个子目录。这次统一忽略了整个目录，代价是视觉决策索引只能按主仓库的绝对路径交给子代理。
- **主分支和功能分支的分工没写**：状态文件按 forge-eng 的规矩只在主分支检出里改，工程文档、验收手册在功能分支上写；两边都要改文档入口和索引。Skill 没提醒「调度产物要在拉分支之前提交」，顺序反了以后合并会冲突。
- **灰区表对「设计已定稿」的项目没用**：五个视觉灰区全被设计阶段答过，真正的灰区在工程侧（提示音、文件划分、测试方式、预览方式），表里没有对应的类型，只能自己补。
- **没有统一启动入口时谁起服务没说**：forge-eng 和 forge-qa 都要求「验收地址必须来自统一启动入口，不得猜」，纯静态项目根本没有这个入口；这次由调度器起服务、核对进程确实属于隔离副本，再把地址交给验收。
- **同一处偏离在三个 Skill 之间传了一圈没人改**：主按钮颜色过渡是设计实现引入的，工程记下来交「待拍板」，验收判为低级别失败又交回设计；forge-dev 作为调度者也没有「谁负责改设计文档」的规则。
- **思考文档认不出**：检测脚本和 `/forge` 一样只找 `brainstorm-*.md`，认不出放在归档目录里的需求讨论；这次有 PRD，不受影响。
- **非交互运行只能代答**：三个硬卡点（灰区确认、执行计划确认、交付确认）都要弹选择框，示范里全部由 AI 代答。
- **不适合宣传的地方**：这一棒整体耗时很长——验收里有一项按真实时间等满一整段专注；子代理交回的汇报里有不少统计数字，调度器都要自己再核一遍才能写进记录。宣传时适合讲「一个命令按顺序调度三个 Skill、每步都有人（AI）核对」，不适合讲「一键几分钟出成品」。
