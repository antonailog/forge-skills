# forge-bugfix

## 输入

- 用户反馈（原话）：「到点切换的时候，开始按钮的颜色是慢慢变过去的，不是一下子换掉。设计里写的是直接切换。」
- 功能分支 `eng/pomodoro-timer-2026-10-23`（QA 通过时的版本）。同一个问题 forge-qa 已记为 `docs/QA.md` 的 BUG-001，`docs/ENGINEERING.md` 技术债和需求设计文档 `docs/modules/番茄钟.md` 的待拍板里也都写过，当时默认「接受现状」——这次用户的反馈等于对这条待拍板给了不同的答案。
- 设计依据：`docs/DESIGN.md` 第五节「颜色和文字直接切换，无过渡」「全页唯一的过渡是按钮悬停变色」。
- 并行情况：另一个会话同时在跑主线（forge-review → forge-ship 把功能分支合进 main → forge-doc-release）。本次修复从功能分支拉，不碰功能分支和它的隔离副本。

## 用户会怎么说

「到点切换的时候，开始按钮的颜色是慢慢变过去的，不是一下子换掉。设计里写的是直接切换。修一下。」（或者 `/forge-bugfix` 后贴这句话）

## 过程

1. **巡检和读资料（P0–P1）**：项目里还没有「谁在跑」登记表 `.forge/active.md`，从模板建一份；Skill 要求先声明功能域（这个项目的业务分块）才能往下走。
   - 演示时由 AI 按默认确认：功能域按页面分成四块——计时、提醒、记录、外观，这个 bug 归「外观」。
   - 读了 PRD、Feature Spec、DESIGN、ENGINEERING、QA 验收手册、bug 历史（之前没有修过 bug）和复盘账本。账本里挑出三条带进本次：根因要能回答「改变某个条件，现象会怎么变」；新加的检查先用已知的坏样本证明它会报失败；共享仓库只按路径提交。
   - 找到相似历史：QA 的 BUG-001 已经给出根因定位。演示时由 AI 按默认确认：沿用它当第一个假设，但照样先复现、再用实验证实。
2. **确认范围（P2）**：只修这一个 bug，编号 BF-1023-1；当前没有别的会话占用「外观」这一块，可以并行。按 Skill 新加的规矩，先列出本次要碰的仓库外写操作：推送修复分支、开合并请求、合并合并请求。
   - 演示时由 AI 按默认确认：同意推荐范围（A）；三项仓库外写操作按示范规矩一次授权。
3. **建隔离副本、登记（P3.1）**：从功能分支拉出 `bugfix/bf-1023-1` 和隔离副本 `.worktrees/bf-1023-1`，在登记表里写下「哪个会话、在哪个副本、修哪个 bug、哪块功能」。项目没有统一的启动命令，就在副本里起一个本地静态服务，换一个和 QA 不同的端口，记下进程和工作目录，确认页面确实来自这个副本。
4. **建报告（P2.5）**：Skill 排在建副本之前，但那样报告会写进主分支的工作区——那是主线会话的地盘。改为副本建好后立刻建 `docs/bugfix/reviews/BF-1023-1.md`，同时在 `docs/bugfix/backlog.md` 登记一行。
5. **复现（P3.4）**：用户要求不做按真实时间等待的测试，而按钮的颜色过渡偏偏是按真实时间走的（假时钟管不到它）。办法是用浏览器调试接口把页面的「动画时钟」停住：过渡一旦出现就停在起点。于是切换后立刻读到的颜色只有两种结果——直接换掉就是新颜色，有过渡就还是旧颜色。写成回归脚本 `scripts/qa/phase-switch-color.mjs`：五种切阶段情形（专注到点、点跳过、鼠标停在按钮上时到点、休息到点、刷新后恢复）加五条守护项（悬停的柔和变色不能被一起去掉）。修前跑：四种切阶段情形全部复现——阶段字已经变成灰青的「休息」，按钮还停在砖红。
6. **根因：先实验，再下结论（P4）**：每个实验只往页面里临时注入一处改动、不改仓库代码，跑同一套检查：
   - 去掉按钮的过渡 → 切阶段全部直接换色，证实过渡就是来源；但悬停的柔和变色也没了，不能这么修。
   - 只改样式、把过渡挪到「鼠标悬停」状态上（QA 建议的改法）→ **鼠标停在按钮上时到点仍然渐变**，鼠标移开时也不再柔和。说明样式层分不清「悬停」和「换阶段」——浏览器只看变化之后的样子，不看变化是怎么来的。
   - 在阶段真正变化的那一刻，让按钮正在进行的颜色过渡立即走完 → 全部通过。
   - 定了方案之后又补一条守护项「计时进行中、鼠标停在按钮上，页面每次走秒都不能打断悬停变色」，并按账本教训先注入一个故意写坏的修法（每次走秒都把过渡走完），确认这条检查会报失败，再信它的「通过」。
   - 5 Whys 结论：悬停变色和阶段换色共用按钮的同一个颜色属性，样式分不清两者；只有页面行为代码知道「这次是换阶段」。
   - 演示时由 AI 按默认确认：根因成立；方案选 A「换阶段时由行为代码让这次换色立即完成，样式规则不动，只在样式文件开头的接口说明里补一句约定」，不选纯样式改法 B（实验已证明修不全）。
7. **修代码（P5，codex-delegate）**：Claude 先把红灯用例、报告、登记一起提交。然后按 codex-delegate 写任务书交给本机 Codex：背景和根因指向报告、验收标准写成能判对错的条目（回归脚本全过、单测全过、只在阶段真正变化时处理、只结束按钮颜色这一种过渡、出错不能连累页面其他更新、不靠改测试过关）、只许改哪两个文件。Codex 很快交回，改动只有几行；它如实写了「沙箱里打不开浏览器，浏览器检查没跑」。Claude 读完整改动、亲自跑回归和单测，全过后提交，提交信息注明由 Codex 实现和作业编号。
8. **同类风险扫描**（项目规则「举一反三」）：全页只有两处过渡，另一处「跳过」按钮的颜色不随阶段变；阶段字没有过渡。结论：没有同类问题。
9. **报告改为待验收（P5.3）**：填根因、修复记录、修前修后同一条命令的红绿证据、五条给用户看的人工验收步骤（含两条边界：鼠标停在按钮上时到点、系统开了「减少动态效果」）。
10. **自动验收（P6，forge-qa Mode B）**：用 Skill 工具调用 forge-qa 的单 bug 回归模式，传入报告、副本、提交和页面地址。forge-qa：
    - 核对页面确实由这个副本里的进程提供；
    - 按人工验收指南逐条走一遍，每个状态节点截图并读颜色和过渡（同样冻结动画时钟、零真实等待）；
    - **同一个脚本再跑一遍修前的页面**（从修前提交导出、临时起在另一个端口，用完关掉），拍出同一时刻的修前修后对照：修前切换类两项失败、悬停和减少动效两项通过，修后全部通过；
    - 回归：修复自带的回归脚本、单测、原有验收脚本里不需要真实等待的用例全部通过，控制台零错误、零外部请求。原有脚本里有几条会在取色前真实停顿一下等过渡走完，按「不做真实时间等待」不跑，它们覆盖的悬停和切阶段颜色由新的零等待检查代替。
    - 回填报告的环境身份、闭环断言、逐项截图和断言。之后 forge-bugfix 跑报告完整性校验器，通过。
11. **用户最终验收（P6.5）**：
    - 演示时由 AI 按默认确认：五条人工验收项按 QA 截图和断言判通过，最终结论 PASS、没有新发现。其中两条真人验要等满休息或专注时长，按「不做真实时间等待」以 QA 的假时钟证据代替。
12. **等主线、合主线、重跑回归**：回来查时主线已经把功能分支和发布后文档同步都合进了 main。把 main 合进修复分支，冲突只有页面行为文件：上线前审查改写了刷新页面的那段代码，还定了新规矩「只在存储和声音两处捕获错误，其余出错要在控制台暴露」——修复里那层错误捕获正好不符合。取主线版本后，把返工意见发回同一个 Codex 会话（codex-delegate 的「返工接回原会话」），让它按新写法重新落修复：不用错误捕获，改为先判断浏览器有没有这个能力。Claude 验收后提交合并，并**再调用一次 forge-qa Mode B** 在合并后的代码上重跑同一套回归，全部通过。
13. **文档同步**：需求设计文档盯着页面代码文件，代码改了文档没改，项目的文档检查会拦下。用 forge-feature-doc 更新：待拍板里删掉这一项、「交互与细节」写明悬停仍柔和变色而切阶段直接换、关键改动加一行，检查通过。另把工程文档的技术债、工程变更日志、验收手册里「未修复」的说法同步成已修复，并在验收手册的回归清单里加上新的回归脚本。
14. **合并（P7）**：合并预演在一个临时的、指向远程 main 的独立检出里做（Skill 写的是在主检出上预演再撤销，但主检出是主线会话的工作区），无冲突，用完删掉。
    - 演示时由 AI 按默认确认：合并（A）。按示范要求走合并请求（[#3](https://github.com/antonailog/forge-demo-pomodoro/pull/3)）而不是本地直接推 main：推送前查了一遍公开仓库不该有的东西，把报告里三处本机绝对路径改成相对仓库根目录；拉取远程后再预演一次，推送修复分支、开合并请求（可合并、无冲突，仓库没有远程自动检查），用保留分支历史的方式合并，再把本地 main 快进到远程 main，确认 main 的内容和回归过的修复分支完全一致、单测和文档检查通过。
    - 演示时由 AI 按默认确认：隔离副本和本地分支先保留（里面有 Codex 任务书和 QA 运行文件，是这次记录的截图来源），清理交给 forge-status。
15. **结案（P8）**：报告移到 `docs/archive/raw/bugfix-reviews/`、状态改为已归档，backlog 那一行移到「已处理」并改链到归档路径。因为走的是合并请求，这一步放在合并之前的最后一个提交里，随合并一起生效。登记表里那一行按 Skill 留着，等复盘或 forge-status 清理。原 bug 已通过、没有新发现，「通过后的新问题分流」不触发；按 Skill 默认不写记忆。最后关掉本地服务，确认没有残留的浏览器、Codex 或服务进程。

**codex-delegate 小结**：两个作业。第一个是修复本身，一轮交回、一轮验收通过；第二个是合并主线后的返工，发回同一个 Codex 会话（不重新读仓库），同样一轮通过。没有收回由 Claude 自己写。两次 Codex 都在最后一条消息里如实写了「浏览器检查没跑」，浏览器层面的验收都由 Claude 和 forge-qa 完成。

**forge-qa 小结**：被调用两次，都是 Mode B（单 bug 回归）：第一次在修复后，第二次在合并主线、修复代码写法变了之后。两次都只回填 BF 报告（环境身份、闭环断言、逐项截图与断言、闭环记录），没有改 `docs/QA.md`、没有做 User Gate（那一步归 forge-bugfix 的用户验收）。

## 问题

- **最值得修：合并阶段默认「本地直接推 main」，主线变了也不要求重新验收。** P7 的合并命令是本地合并后直接推 main，P8 结案排在合并之后；走合并请求时，结案归档只能挪到合并前的最后一个提交里，Skill 没写。更要紧的是 P7 只说「主分支有新提交就先变基解决冲突再合并」，没要求解决冲突后重跑回归、重新验收——这次主线的上线前审查恰好改写了修复所在的那几行，还定了新的错误处理规矩，修复不得不按新写法重写一遍；要不是任务里明确要求重跑，照 Skill 字面就会带着没验过的代码合进去。
- **并行登记看不见真正的撞车**：`.forge/active.md` 只有 forge-bugfix 会登记，主线的 forge-review、forge-ship 都不登记（forge-status 那棒已指出）。这次的实际冲突正是主线审查和本次修复改了同一个函数，登记表却显示「外观这块没人占用、可以并行」。另外 P0 打印「当前并行会话」时会把模板注释里的示例行当成一个会话打出来。
- **建报告排在建隔离副本之前**：P2.5 建报告在 P3 建副本之前，照做会把报告写进主分支的工作区——并行时那是别的会话的地盘。这次调成副本建好后立刻建报告。
- **「修回原设计就不用更新需求设计文档」和实际冲突**：P8 这样写，但这个偏离早被记成需求设计文档的待拍板，用户的反馈等于拍了板；而且需求设计文档盯着页面代码文件，不更新它项目的文档检查会直接拦下。QA 验收手册的「未修复问题」、工程文档的技术债这些也把它记成未修复，P8 的同步清单里都没有。
- **合并预演要在主检出上做**：P7 预演是在主检出上切到 main、试合并再撤销；并行时主检出是别的会话的工作区。这次改在一个临时的独立检出里预演，用完删掉。
- **合并后立刻删隔离副本会丢证据**：P7 推荐项包含删副本和本地分支，但副本里被忽略的 Codex 任务书、QA 运行文件正是这次记录的截图来源，也和 forge-status「删副本要先备份核对」的规矩冲突。这次保留，交给 forge-status。
- **按时间变化的视觉问题没有复现方法**：复现引擎只列浏览器、Playwright、纯代码；颜色过渡跟着页面的动画时钟走，假时钟管不到，按真实时间采样又慢又看机器快慢。这次自己想了「冻结动画时钟」的办法，Skill 里没有，验收报告校验器也只查「有没有截图」，不管结论是否稳定可复现。
- **谁填哪一节有矛盾**：P5.3 要 forge-bugfix 填「用户问题闭环断言」，但这一小节在「QA 测试过程」节里面，而同一份手册又禁止 forge-bugfix 填这一节；第 7 节验收入口也是 forge-bugfix 写草稿、forge-qa 再改。报告模板也没带文档规范要求的 `status` 头信息，要自己补。
- **非交互运行只能代答**：功能域声明、范围确认、根因与方案确认、合并方式、用户最终结论五处都要停下问人，演示里全部由 AI 代答。
- **不适合宣传的地方**：
  - 用户最终验收是 AI 按 QA 证据代答的；其中两条真人要等满休息或专注时长，这次用假时钟证据代替，没有真人看过。
