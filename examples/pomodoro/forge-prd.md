# forge-prd

## 输入

上一步的思考文档 `docs/archive/raw/discussions/番茄钟/2026-10-23-番茄钟-需求讨论.md`，以其中「整合后的最终决策」一节为准。项目里还没有 PRD、变更日志和任何代码。

## 用户会怎么说

「按刚才讨论的结论，写 PRD 和 Feature Spec。」

## 过程

1. **定位**：搜项目里的 PRD 和变更日志，都没有，进入「从零创建」模式，并标记最后要新建变更日志。
   - 演示时由 AI 按默认确认：进入创建模式。
2. **登记功能**：起名 `pomodoro-timer`，建功能状态文件，在功能登记表里登记，PRD 阶段标为「进行中」。
3. **理解现状**：仓库里没有代码可读，直接以思考文档为准。Skill 要求的几轮确认（产品定位、功能边界、技术约束、已知问题、后续规划）都已在头脑风暴里答过。
   - 演示时由 AI 按默认确认：五轮确认均沿用思考文档和需求方设定的结论。
4. **诊断与审查**：新产品，自动走「深度审查」。
   - 十星挑战：现在的方案是「刚好够用」的版本；十星版本能察觉你是不是真在专注、避开会议、和同事一起开始一段专注。差距大，超出这次范围，不做。
   - 假设审查：挑出两个原先默认成立、其实不一定成立的前提——「浏览器一定能保存记录」（隐私模式可能不行）和「只会开一个页面」（同事可能开两个），各补了处理规则。
   - 反驳：「到点有提醒」在后台标签页里做不到分秒不差，验收不写「准时」，改成「后台必须响、并记录晚了多久」。另外补了一条讨论里没定的规则：待开始时也能「跳过」，刚专注完想直接再来一段不用绕路。
   - 演示时由 AI 按默认确认：同意诊断方向。
5. **方案确认**：把六块功能（计时与控制、今日完成数、到点提醒、标签页标题、保存与恢复、手机与窄屏）逐块列出「做什么、不做什么」，汇成变更清单。
   - 演示时由 AI 按默认确认：变更清单确认。
6. **写 Feature Spec 并自审**：按模板写用户流程、页面结构、每块功能的正常 / 异常 / 边界场景、异常态表和验收检查表。交给需求方前按 Skill 的四点自审过一遍，查出两处：一句「无过渡动画以外的动效」意思含糊，改成「不出现持续循环的动画」；「离开期间到点后重新打开」时页面上那行状态文字显不显示没写，补上「不显示」。
   - 演示时由 AI 按默认确认：Feature Spec 确认，进入写入。
7. **项目 CLAUDE.md**：已存在但没有「Forge 工作流」一节，按模板追加到末尾。
8. **写入文档**：新建 PRD（产品当前事实 + 给后续 AI 的交付说明）、PRD 变更日志（含本次关键决策表，并按 git 历史回溯了项目初始化）、Feature Spec；功能状态改为「PRD 已完成」，登记表更新时间；顺手把新文档加进文档入口和索引。
9. **同步需求设计文档**：Skill 最后一步要求调用 forge-feature-doc，交给下一步。

## 问题

- **功能登记表两套表头**：forge-doc-policy 的脚手架建的登记表是「功能 / PRD / 设计 / 工程 / QA / 最后心跳」，forge-prd 要求的是「功能 / 版本 / 状态 / 负责 Skill / 心跳 / 分支 / 描述」。这次表里还没有行，直接换成了 forge-prd 的表头；两个 Skill 需要统一。
- **「确认前不写文件」与「第一步就建状态文件」打架**：Skill 铁律说用户确认前不得写任何文件，执行细则却要求一开始就建功能目录和状态文件。没说状态文件算不算例外。
- **问题归因不适用于新产品**：归因只有「设计缺陷 / 实现偏离 / PRD 遗漏」三类，都默认已经有 PRD 或代码。从零创建时没有对应的类别，只能跳过。
- **和头脑风暴重复提问**：从零创建要求再做五轮确认，内容和头脑风暴已经问过的高度重合，Skill 没说「有思考文档时可以直接沿用」。真实使用时用户会被问两遍同样的问题。
- **引用了这里没有的可视化工具**：Skill 多处要求用一个专门的小部件工具画对比图、仪表盘，当前环境没有这个工具，只能用文字和表格代替。
- **异常态凑数**：规定每个功能点至少写三种异常态（空态、错误态、降级态）。「到点提醒」根本没有空态，只能写「不适用」。
- **视觉验收项写不出具体值**：模板要求从设计文档里抄颜色、字号等具体值，但 PRD 在设计之前写，此时还没有设计文档，只能先写不依赖具体值的约束，并注明「设计定稿后回填」。模板里没有这种情况的写法。
- **项目 CLAUDE.md 越来越长、还有重复**：脚手架生成的 CLAUDE.md 开头写着「索引层文件，只保留必要入口和硬约束」，forge-prd 又追加了一大段规则，和原有的「走 Forge 体系」一节部分重复；追加的「文档位置」把 `docs/QA.md` 写成「QA 报告」，而文档治理规范里它是「验收手册」。
- **Feature Spec 模板开头的说明过时**：模板第一行说 Feature Spec「插入到 PRD 对应功能章节之后」，和 Skill 正文「不把完整 Feature Spec 塞进 PRD」相反。
- **没说要更新文档入口和索引**：forge-prd 写完 PRD 后不提文档入口和索引，这次是按文档治理规范自己补上的；不补的话，从入口点不到 PRD。
