# forge-fupan

## 输入

- 番茄钟示范从头到尾的各份示范记录（本目录 `forge-doc-policy.md` 到 `forge-bugfix.md`，按进度表的先后），当作这次项目「会话」的完整经过。用户原话取自每份记录的「用户会怎么说」；记录里只写了日期 10-23，没有具体时刻。
- 项目仓库 `antonailog/forge-demo-pomodoro` 的 main（只读）：交付物、关键文件、关键代码都从这里取。复盘范围从搭文档骨架到修复合并（合并请求 #3），不含旧版复盘那次提交。
- 新版 Skill 本体：`skills/forge-fupan/SKILL.md`、`references/`、`scripts/build.py`。

## 用户会怎么说

「项目做完了，复盘一下：这次哪些做法值得带走，我下次该怎么跟 AI 说。」（或者直接 `/forge-fupan`）

## 过程

按新版 Skill 的九步走：找会话 → 压摘要 → 启动提问 → 写工作总结 → 写工作复盘 → 写知识拓展 → 出页面 → 自查 → 收尾。

1. **找会话、压摘要（第 1–2 步）**：**改道**——这个示范没有单独一份会话日志，按 SKILL.md「找不到会话日志」那一行处理，`find_session.py`、`digest.py` 都跳过，直接读示范记录；启动消息和摘要的结果一行都注明「素材为示范记录」。另读了仓库的提交记录：整件事的时间范围取第一次提交到修复合并那次提交（北京时间 10-23 14:57—18:51），过程回顾各段只写日期、不写具体时刻。
2. **复盘根目录**：**改道**——用环境变量 `FUPAN_ROOT` 指到临时目录，不碰用户真实的复盘目录和汇总页。项目名「番茄钟」；模块名按规则找项目文档里现在的叫法，需求设计文档写的是 `module: 番茄钟`，所以也叫「番茄钟」。
3. **启动提问（第 3 步）**：按 startup.md 写好一条启动消息（做了什么、变化、关键词、打算写的盲区 / 专题 / 延伸），存成复盘文件夹里的 `_启动消息.md`。关键词用 `build.py --known-terms` 查过；临时目录里没有以前的复盘，全部是「第一次见」。
   - 演示时由 AI 按默认确认：回「好」，按列出的全部写（需求方是想了解用 AI 做一个小项目全过程的普通人，没有另外点名想学的）。
4. **写一、工作总结（第 4 步）**：
   - 过程回顾按用户的需求转折切成五段：定需求、定外观、写代码并验收、审查合并和文档同步、修 bug（和上一段并行）。
   - 关键决策十三条，按 Skill 的八种来源逐条判定。需求方的拍板在示范里都是 AI 按设定代答的，判来源时当作需求方本人的回答，并在附带发现里写明这一点。
   - 结果评估：两个主目标（番茄钟打开就能天天用 → 待验证，因为后台到点晚多少没实测；第一版合进主分支 → 达成，部署移出范围），两个衍生目标（切阶段按钮直接换色、暂停后继续马上走）。
   - 交付物：番茄钟页面（用验收时的四状态总览图当截图）、公开仓库、三个合并请求（修复那个配修前修后对照图）；十份关键文件；三组关键代码（计时规则、页面接线、页面与样式），讲解逐条对照代码写，行号交给 build.py 按函数名算；其余产出按需求、设计、工程、验收、文档工具分组。
   - 遗留事项五条：后台到点等手动验、要不要加桌面通知、要不要部署、仓库加自动检查、功能状态没更新到「已发布」。
5. **写二、工作复盘（第 5 步）**：
   - 对标分析按「用 AI 从零做一个小网页工具」的业内路径排了十一步，结论：一致 7、待改进 3（测试质量、真实环境验收、发布时文档一起进）、缺失 1（合并前自动检查）。需求访谈那一步加了方案全景图（现成工具、可安装应用、本次单页静态网页）。
   - 外链共 36 个，全部联网打开核对过（Anthropic、GitHub、MDN、Chrome、Playwright、Node.js、Martin Fowler、Google 工程实践、Scrum 指南等），note 写原文意思。Codex 的官方文档地址已跳转到新域名，按跳转后的地址写。
   - 需求表达两条：「待拍板默认接受了，发布后又要改」（需求不一致）、「说发布时没说要带上文档」（需求不完整）。**理解**：SKILL.md「找不到会话日志」那一行写着需求表达整节不写，但这次的用户原话由示范记录明确给出，不是凭记忆复述，所以照常写，原话时间写成「10-23 · 发布后」这类先后。
6. **写三、知识拓展（第 6 步）**：知识地图按这次的流程分六层（需求、设计、实现、验收、发布、维护）；条目八条——专题 1（用 AI 做一个小项目的完整流程，来源是「这次哪些做法值得带走」）、盲区 5（浏览器的后台和出声限制、验收标准要能判对错、测试本身也要审、待拍板不回就是同意、合并请求上的自动检查）、延伸 2（部署到 GitHub Pages、后台准时的桌面通知）；关键术语六个模块各五个词。条目多于 3 条，Skill 允许派子 agent 并行，这次没派，自己写。
   - **改道**：延伸学习的第二条原则「用户的长期方向」要读工作区根 README 的长期方向表，那是真实用户的个人方向，和示范里的需求方对不上，跳过，两条延伸都按「这类工作的下一步」推荐。
7. **出页面（第 7 步）**：`build.py` 第一次校验通过但有提醒：结果一行的「做法」超出一个字，八份文档类关键文件没写一句说明。改完重跑，校验通过、没有提醒。最后跑了一次 `build.py --index` 重建汇总页。
8. **自查（第 8 步）**：用无头浏览器打开「打开复盘.html」，三节、十一个小节都在，控制台零错误，点关键文件能打开抽屉看内容。关键代码那张流程图第一版箭头标签挤在一起，简化后重出一次。
9. **收尾（第 9 步）**：**改道**——Skill 要求删掉项目 `.forge/active.md` 里本会话登记的那一行；示范要求不改项目仓库，而且登记表里没有本会话的行，没动。

## 问题

- **「找不到会话日志」那一行和示范素材打架**：原来写「需求表达整节不写」，但示范记录明确给了用户原话。这次照常写了；SKILL.md 已改成「拿不到用户原话就不写需求表达」。
- **时间字段是硬要求，素材里没有时刻**：`session.range` 必须带时分才能通过校验，过程回顾每段也必须填开始时间和耗时；示范记录只有日期。这次时间范围取仓库提交时间，各段只写日期、耗时写「—」。
- **临时目录下「第一次见」失去意义**：`--known-terms` 只查 `FUPAN_ROOT` 下的旧复盘，临时目录是空的，所有词都标「第一次见」。对示范的需求方（第一次复盘）说得通，但不是 Skill 设计的本意。
- **页面数据里带本机路径**：`data.js` 记着每个文件的本机路径（本地打开、跳到编辑器用）。对外展示只放截图。
- **项目名和模块名重名**：按规则，项目叫「番茄钟」、需求设计文档的模块也叫「番茄钟」，文件夹成了 `番茄钟/番茄钟/`。只有一个功能的小项目都会这样。
- **关键术语的两条要求互相挤**：「每块 3–5 个词」和「对标分析里各步的关键词也汇总进来」同时满足不了，这次挑重要的进术语表；write-knowledge.md 已改成「挑影响方向的汇总进来」。
- **不适合宣传的地方**：素材是示范记录，不是真实会话；需求方的每一处拍板都是 AI 代答的；「第一次见」全部亮着是因为临时目录里没有以前的复盘。
